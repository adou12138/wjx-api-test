# 关键陷阱详解（实测血泪）

> `SKILL.md` 只保留 18 条陷阱的**一句话规则**用于快速对齐；本文件是每条规则的完整依据、
> 实测案例与正确做法。**设计用例前、复测前、结果归因时**读一遍——这些坑全部是真实踩过的。

1. **不要只验 `result=true`**
   接口返回成功不代表数据真的落地。永远调用独立查询接口回读验证（C 系列 + `framework.md` §9.4
   辅助验证矩阵），否则得到的是"假通过"。

2. **异常用例必须命中错误关键词**
   只看 `result=false` 不够——错误语义不准（比如参数名写错、返回了无关错误）也会绿灯。
   必须断言命中文档化的 `err_exact` 关键词。

3. **安全拦截 ≠ 缺陷**
   `<script>` / DOM 注入被拦下是**预期行为**，记「符合预期」而不是缺陷。误记会造成假缺陷。

4. **内容安全 ≠ 代码安全**
   接口常防可执行代码，但**不防违规词**（如"赌博/色情"这类内容风险词）。实测：标题写违规词
   仍创建成功，系统未拦。这是真实缺口，单列 N1/N2 类。

5. **（仅当确实做了多环境对比时）多环境差异记 ENV，不擅判**
   若在多个环境跑了同一请求、出现"一个拒一个默认"的差别，那是环境/配置差异，先记 ENV 台账、
   不擅判缺陷。但**多环境对比本身不是必做步骤**——默认只测用户指定的那一个环境。

6. **别被限流 / 防重提交污染结论**
   单接口串行复测时正文加随机串 + 间隔 ≥0.4s，否则会把限流/防重误判成"词库不稳定/误拦正常内容"。

7. **CSV 用 utf-8-sig 逗号分隔**
   字段含逗号/引号/换行时用双引号包裹（内部引号用 `""` 转义），否则 Excel/WPS 打开错位。
   （团队约定：交付数据一律 CSV，不用 TSV。）

8. **连接异常重试后仍失败 → ENV**
   不计入业务缺陷。重试次数由 `RETRY_COUNT` 控制（可经执行配置 `execution.retry_network_errors` 覆盖）。

9. **测试地址必须取自接口文档『接口地址』**
   禁止写死默认域名；接口路径会随文档变化，以文档标注的实际地址为准。用
   `kb_load_contract.py --endpoint` 自动抽取，再经 `WJX_BASE_URL` 传入。

10. **不是每个接口都支持所有功能**
    测试前必须做适用性判断（第 1.5 步），不支持的功能标 N/A，不强行套用——例如给创建接口测
    "导出下载"、给查询接口测"状态机"，强行套用只会产生误报。

11. **辅助验证要用独立读接口**
    测写接口时用查询/列表/统计等**读接口**交叉验证，不要用另一个写接口验证写接口（互相污染）。
    辅助接口本身应先通过冒烟，否则验证结果不可信。

12. **并发 / 性能(J 维) 必须先探明并尊重服务端限流阈值**
    爆发并发（远超"每秒 N 次"上限）会触发限流，使"错误/数据错位"被误判为接口缺陷——实测曾把
    限流误判成"并发串数据"。正确做法：
    ① 先探出限流文案与阈值（如"查询频率过快，每秒只允许查询10次"）；
    ② 并发用例统一经限速器（如 ≤阈值/s，间隔 ≈0.1s）隔离限流噪声；
    ③ "数据不串"类断言的**预期值必须来自同一接口的串行预取基准**，不可用全量视图等其他来源
    （口径不同会假错位）；
    ④ 区分"真缺陷"与"限流 ENV"——报错文案含限流/防重提交字样的不计缺陷。

13. **参数校验必须断言"应被拒绝"（B 维度最隐蔽盲区）**
    B 维度的核心断言是"非法 / 缺失 / 类型错 / 枚举越界输入 → 应被拒绝"。**严禁**把非法输入断言成
    "应当成功"（`expect_success=True` 配给非法输入）——一旦宽松接口接受非法值，用例反而判 PASS，
    缺陷被完全掩盖。实测 1006001 接口因此漏报 5 条参数校验缺陷（枚举越界/类型错/空值/必填缺失
    全被接受却判通过）。非法/缺失输入一律用"期望被拒绝"的断言（运行器已封装
    `assert_validation()`）；仅当产品明确约定某非法值有文档化默认/容错时，才允许接受并记「符合预期」。

14. **反向盲区：过度校验（"假失败"，与第 13 条对称）**
    第 13 条只防了"欠校验"，反向同样会漏——**文档标注为可选/可空的字段，传 `null` / 空串 / 不传时
    却被接口拒绝**。此时用例判 FAIL，极易被人工归因为"需求就是这样"，缺陷被静默漏报。
    **最高发触发点：把读接口返回的结构原样回写给写接口**——实测：获取外观设置返回的 data 直接
    传给保存外观设置，报 `The BackgroundImage field is required.`，而该字段本可为空。
    做法：可选字段一律用 `assert_no_over_validation()` 断言"应成功"；每个可选字段跑
    **缺失 / `null` / `""` / `[]` 四态**（`check_null_triad()`）。

15. **纯接口视角测不出前后端不一致（AB 维度）**
    接口自身"跑得通"不等于用户能用——历史缺陷中约 8.4% 是"页面能操作但接口报错"或"接口允许但
    页面不允许"。只要被测接口在前端有对应操作，就必须**以页面基线作为预期值**做比对（权限/校验/
    展示/枚举/默认值/边界六类口径），基线来源见 `references/ui_baseline.md`。共享、协作、子账号、
    资源管理员四类场景是重灾区。

16. **错误信息要验"根因没被掩盖"**
    不同成因的错误必须给出不同错误信息。实测缺陷：传错 roleId / 用户名 / 时间戳，一律提示
    "sign 验证失败"；缺少 appId 也报"验签失败"——根因被掩盖，排查被彻底误导。做法：分别构造
    "凭证错误"与"参数缺失"两种请求，断言二者错误信息**必须不同**（`check_error_root_cause()`）；
    同时扫描错误信息中是否残留未渲染的模板占位（如 `Email[]`、`{0}`）。

17. **回归复测时，套件自身是最大误报源**
    接口修复后直接重跑旧套件会制造"假缺陷/假通过"。实测（1006001 复盘）踩过三类：
    ① **过期期望误报**——修复后旧期望把已修好的行为判 FAIL（如期望字段集还是改名前的 PascalCase）；
    ② **空转假通过**——检查逻辑引用旧字段名取不到值，循环零次恒 PASS；
    ③ **硬编码 finding 污染台账**——finding 文案无条件 append，检查 PASS 也落旧缺陷。
    预防：复测前核对受影响用例的期望值；断言循环必须校验"至少遍历 N 个元素"（`assert_non_empty()`）；
    finding 只在判 FAIL 的分支内记录；复测结束把台账逐条回写"已修复(附证据)/仍存在/新发生"，
    上轮基线单独备份（另见 `defect_patterns.md` 回归复测专项、`framework.md` §6 末 4 项）。

18. **问题单「请求Body」必须含公共参数**
    公共固定参数 `encode`/`appid`/`action`/`sign`/`ts` 一个都不能少，否则开发无法原样复现。
    实测踩过：独立测试脚本只手填业务参数，漏掉公共参数，问题单被要求返工。
    **运行器已自动补齐**——`api_test_runner.add_finding()` 对含 `action` 字段的原始报文自动补齐
    全公共参数（只补缺失项、不覆盖已显式传的值；`ts` 用占位符）；**独立脚本（不调用运行器 helper）
    必须自行补齐**，可调用运行器导出的 `complete_request_body()`。
    例外：仅当缺陷本身就在测"缺某公共参数"（如缺 action 仍成功），body 才故意不含该字段。
