# 高频缺陷模式清单（启发式检查表）

> **用法**：设计用例**之前**过一遍本表，逐条问"这个接口会不会也有这个问题"。
> 本表来自真实历史缺陷的统计归纳，按命中频率排序。命中率高的模式优先安排用例。
> 每条给出：典型现象 → 缺陷样例 → 对应维度 → 验证方法。

---

## 使用方式

1. **设计前**：按 Top 1–12 顺序过一遍，勾出本接口可能命中的模式。
2. **设计中**：把勾中的模式转成具体用例，挂到对应维度编号下。
3. **复盘时**：回到本表，检查是否有"用例全绿但本表某条没测"的情况。

---

## Top 1　响应字段缺失或冗余（命中率最高的单一模式）

**典型现象**：响应缺少文档声明的字段；或返回了大量无用/重复的字段。

**缺陷样例**
- 接口文档中声明的字段，实际响应里没有返回。
- 「是否匿名」这类列表级常量，在每条记录里都重复返回（应上提至响应顶层）。
- 传入 `taskid` 后没有返回任何数据。

**对应维度**：K1 消费者契约、K3 契约回归、Y1 子类型结构完整、AA9 字段冗余

**验证方法**
- 拿文档字段清单与实际响应做**双向 diff**（多了什么、少了什么）。
- 列表接口检查是否存在"每条记录都一样的常量字段"。

---

## Top 2　页面与接口行为不一致

**典型现象**：同一个操作，页面能做成但接口报错（或反过来）。

**缺陷样例**
- 共享文件夹中的问卷，问卷管理员在页面可修改，接口却报 `The survey does not belong to the current user`。
- 分配给问卷管理员的问卷，接口允许删除，但页面不允许。

**对应维度**：AB1 权限口径、AB2 校验口径、AB3 展示口径、AB4 枚举口径

**验证方法**
- **以页面基线为预期值**：先在页面操作并记录结果，再用接口做同样操作，二者必须一致。
- 共享 / 协作 / 子账号 / 资源管理员**四类场景必测**。

---

## Top 3　事件推送丢失 / 重复 / 载荷不准

**典型现象**：事件没推、推了多次、或推送内容与实际情况对不上。

**缺陷样例**
- 创建了 8 个 Webhook，只推了 1 个，其他都没收到。
- 按子账号订阅了问卷状态更新事件，事件触发了但无推送记录。
- 全局订阅下，创建问卷后同时产生"创建"和"更新"两条记录。
- 并发作答时日志数量少于实际数量（实际 50，日志 31）。

**对应维度**：AD1 事件完备、AD2 不丢失、AD3 不重复、AD4 载荷准确、AD5 订阅范围、AD9 并发一致

**验证方法**
- **枚举遍历所有事件类型**，不能只测一个。
- 触发 N 次，断言收到 N 条（含批量操作的推送语义）。
- 全局 / 按用户 / 按资源 × 主账号 / 子账号 做订阅范围矩阵。

---

## Top 4　文档与实际不符

**典型现象**：文档写的是一回事，接口做的是另一回事；或文档本身不可用、不安全。

**缺陷样例**
- Swagger 页面加载失败，请求 `/swagger/index.html/swagger.json` 返回 404。
- 方案约定 `/openapi/v1.json`，实际是 `/swagger/v1/swagger.json`。
- 全量 API 文档（1009 paths）匿名可访问，且 CORS 任意 Origin 反射 → 信息泄露。
- 文档中找不到已上线的 `/v1/surveys/excel-import`。
- 枚举值 1001~1005 实为"每周限制"，文档文案写成"每年"。

**对应维度**：K8 文档可用性与安全、K9 文档-实现一致性

**验证方法**
- 文档地址可访问（含相对路径拼接）、在线调试可用（不 `Fail to fetch`）。
- 检查文档是否应鉴权、CORS 是否任意 Origin 反射。
- 枚举释义逐条比对实现；示例参数直接复制跑一遍。

---

## Top 5　错误信息：语言 / 渲染 / 根因掩盖

**典型现象**：报错信息看不懂、看不出哪错了、或指向错误的原因。

**缺陷样例**
- 传错 roleId / 用户名 / 时间戳，一律提示"sign 验证失败"（真实根因被掩盖）。
- 缺少 appId 参数时也报"验签失败"。
- 邮箱重复时提示 `Email[]`——占位符未渲染，拿不到冲突值。
- 报错信息返回的是变量形式，未转英文/未转 JSON。

**对应维度**：H2 文案具体性、H6 根因不掩盖、H7 渲染完整性、H8 国际化（国际版）

**验证方法**
- **构造两种不同成因的错误请求，断言错误信息必须不同**。
- 扫描错误信息中是否残留 `{0}` / `%s` / `[]` / `{{var}}` 等未渲染占位。

---

## Top 6　枚举释义与取值范围不符

**典型现象**：枚举值的实际含义与文档/文案描述不符；或越界值未被拒绝。

**缺陷样例**
- 枚举值 1001~1005 对应"每周限制"，文案写的是"每年"。
- 传入范围外的数字，没有返回失败提示。
- 获取列表时返回 `0`，但提交时传 `0` 不行——同一个枚举读写不一致。
- 重发类型实际有 -1/-2/-3/-4，传正数反而报错。

**对应维度**：B3 枚举越界、K9 文档-实现一致性、O4 渠道枚举释义

**验证方法**
- 用 `check_enum_exhaustive()` 遍历文档声明的每个枚举值。
- **读写一致性**：列表接口能返回的值，写接口必须能接受。

---

## Top 7　空值被错误接受 或 错误拒绝

**典型现象**：该允许的被拒（过度校验），该拒绝的被接受（欠校验）。

**缺陷样例**
- 可选字段 `BackgroundImage` 传空却报 `The BackgroundImage field is required.`
- 非必填的手机号传 `""`，提示格式错误（应通过）。
- 内容字段传空字符串，竟然创建成功（应提示必填）。
- 修改时间设置时，不该必填的字段被强制必填。

**对应维度**：B8 过度校验、B9 空值四态、K6 空值与默认值契约

**验证方法**
- **往返验证**：把读接口返回的结构原样回写给写接口，必须能成功。
- 对每个可选字段跑四态矩阵：缺失 / `null` / `""` / `[]`。

---

## Top 8　重复数据未校验 / 未去重

**典型现象**：本应唯一的数据可以重复创建；或列表型参数传入重复值未被处理。

**缺陷样例**
- 添加重复的 IP 段或 IP 没有限制。
- 标签 Id 列表传入重复值，未校验也去重。
- 已将某联系人设为管理员，再次设置仍成功（应提示已存在）。
- 自定义字段名重复，提示语却写成"标签名不能重复"。

**对应维度**：AC2 业务唯一性、AC3 列表去重、AC4 错误信息归属

**验证方法**
- 对每个应唯一字段重复提交，断言被拒。
- 断言错误信息中**回显了冲突值**，且**对象名正确**。

---

## Top 9　限流配额归属与阈值不符

**典型现象**：配额到底算谁的、到底是多少，说不清也对不上。

**缺陷样例**
- 主账号与子账号同时请求，tps 各为 10，未按"两者之和为 10"限制。
- 配置 `DefaultQpsLimit=30`，压测实测不到 10。
- 某接口限制了 1，实测 tps 仍为 10。
- 配置列表中 `qps_limit` 已废弃却仍显示在下拉列表里。

**对应维度**：J3.1 配额归属口径、J3.2 配置-实际一致性、J3.4 废弃配置项

**验证方法**
- 分别测主账号、子账号、主+子并发三种情况的实测阈值。
- 对比配置值与实测值，不一致即记缺陷。

---

## Top 10　时区未转换（国际版专项，国内版 N/A）

**典型现象**：接口返回的时间与页面显示差固定的小时数。

**缺陷样例**
- 接口传 `2029-08-24T14:15:22.123Z`，页面显示 `24 8月 2029 22:15:00`（多 8 小时）。
- 获取发送列表，发送时间比页面显示少 8 小时。
- 标签的创建/更新时间未按用户时区转换。
- 只填日期未填时分秒时，时间显示不对（未默认为 0）。

**对应维度**：Z6 时区一致性（见 framework §1.3）

**验证方法**
- **以页面显示值为基线**做比对，差固定小时数即为缺陷，不要归为 ENV。
- 至少覆盖 UTC / +08:00 / -05:00 三个时区各验一遍。

---

## Top 11　字段命名风格不统一

**典型现象**：同一个 API 里混用命名风格，或与文档、与前端不一致。

**缺陷样例**
- 全局下划线风格中，`additionalProperty` 仍是驼峰。
- 获取列表返回 `eventType`，其他接口都是 `event_type`。
- URL 路径中使用 `-` 而非下划线。

**对应维度**：K7 命名风格一致性

**验证方法**
- 用 `check_field_naming()` 扫描响应所有字段名。
- 与文档字段名、与前端字段名做三方比对。

---

## Top 12　可选字段被强制必填

**典型现象**：文档标注可选，实现却强制校验。

**缺陷样例**
- `content` 字段注释后接口返回失败，实际应为非必填。
- 修改时间设置时，除了时间段还可以改其他时间信息，却被强制要求填时间段。

**对应维度**：B8 过度校验、K9 文档-实现一致性

**验证方法**
- 逐个移除文档标注为"可选"的字段，断言仍应成功。

## 补充模式（命中率较低但危害大）

| 模式 | 典型现象 | 对应维度 |
|---|---|---|
| 并发重复与丢失 | 并发操作产生重复数据或丢失数据 | J2、AC5、AD9 |
| 批量部分失败导致整体失败 | 批量中一项有问题，其余全改不了 | X1、Z3、U2 |
| 终态重复操作静默成功 | 已删除再删、已发布再发，返回 true 无提示 | E6、E7 |
| 响应字段语义无效 | 字段有值但无业务含义（返回的 URL 打不开） | C4 |
| 大字段导致超时 | 内容较长时保存极慢或一直不成功 | J1、J4 |
| HTTP 状态码语义错用 | 参数错误返回 200、无凭证与越权都返回同一码 | §9.7 |
| 接口与数据库命名不一致 | 接口字段名与数据库字段名对不上 | K7 |

## 缺陷模式池（自动累积与风险排序，`scripts/bug_pattern_pool.py`）

本表是人工归纳的固定清单；池则把**历轮真实缺陷**沉淀成可累积、可排序的数据（`assets/bug_patterns.json`，冷启动为空、随轮次增长），让"最常翻车 / 最该先看"的类浮出来，反哺本清单的更新。

```bash
python scripts/bug_pattern_pool.py --list                                  # 汇总池内容
python scripts/bug_pattern_pool.py --merge <*_report_full.json>             # 按指纹并入本轮缺陷（幂等）
python scripts/bug_pattern_pool.py --rank <*_report_full.json> --top 8 --out top.md   # 风险排序
```

| 参数 | 说明 |
|---|---|
| `--pool` | 池文件路径（默认 `assets/bug_patterns.json`）；换池须显式指定 |
| `--list` | 列出池内容汇总 |
| `--merge` | 把一个 `*_report_full.json` 里的缺陷按指纹并入池（幂等：同源重复并入不改变池，不同源命中同一模式累加 hits） |
| `--rank` | 对缺陷产物做风险排序 |
| `--top` | `--rank` 输出的条数（默认 8） |
| `--out` | `--rank` 的 Markdown 输出路径（省略则打印到 stdout） |

**边界**：池只做**累积与排序，不自动生成用例**——从一个历史缺陷推断不出修复后的正确行为，自动生成会产生错误断言或与既有生成器重复。闭环落点是"知道什么常翻车 → 人决定补什么测试"。

## 回归复测专项（复测本身会制造"假缺陷/假通过"）

回归复测时接口往往已部分修复，此时**测试套件自身反而成为最大误报源**。1006001 实测复盘踩过三类，任何一次复测前先对照：

| 陷阱 | 现象 | 根因 | 预防 |
|---|---|---|---|
| **过期期望误报** | 接口已修复的行为被套件判 FAIL，被当成"新缺陷"上报 | 套件的期望字段集/枚举/断言方向未随接口修复同步更新 | 修复上线后先人工核对受影响用例的期望值，再下复测结论 |
| **空转假通过** | 校验恒 PASS，实际循环零次什么都没验 | 检查逻辑引用旧字段名（响应改名后 `get()` 全部取到 None，遍历空列表） | 树遍历/字段校验必须断言"至少遍历 N 个元素"，空转即 FAIL |
| **硬编码 finding 污染台账** | 检查明明 PASS，台账里仍出现旧缺陷文案 | finding 描述硬编码且无条件 append，与检查结果脱钩 | finding 只能在对应检查判 **FAIL** 的分支内记录 |

**台账对齐铁律**：复测结束必须把问题台账与结论对齐——每条历史缺陷标注**已修复(附证据) / 仍存在 / 新发生**，上一轮基线单独备份（不覆盖），不允许"待修复"与"已修复"混存。

**对应维度**：§6 假通过盲区清单（回归复测 4 项）、Y2 复杂结构、K7/L2 契约
