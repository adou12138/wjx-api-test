# 接口文档合理性审查（契约审查模式）

> 本文件是 `wjx-api-test` 的**文档审查**能力说明。当用户的意图是「审查 / 校验接口文档是否合理」，而非「执行接口测试」时，进入本模式：**只审文档原文，不发起真实接口调用**。审查结论复用本 skill 的 30 维度框架与 9 列问题台账，便于与后续测试衔接。

## 0. 何时进入本模式

- 触发语：「审查接口文档」「校验文档合理性」「文档有没有问题 / 歧义 / 缺失」「文档字段说明是否准确完整」。
- 与「第 1 步 梳理接口契约」的关系：梳理是把契约读进框架结构；审查是对契约**本身做质量体检**。二者常合并——先梳理（§1 模板）再审查（本文件清单）。
- **不执行接口调用**：本模式产出的是文档层问题（字段说明缺失、示例冲突、错误码不全等），不是接口运行时缺陷。

## 1. 三种契约来源（取原文，禁止手抄偏差）

文档审查的前提是拿到**文档原文**（参数表 / 响应示例 / 错误码表 / 边界说明）。支持四种输入，覆盖用户提到的「粘贴 / 本地文件 / URL 或知识库」三类：

| 模式 | 来源 | 获取方式 |
|---|---|---|
| A 知识库 | L5 KB（含 `project/showdoc_api_docs/`） | `python scripts/kb_load_contract.py --kb <KB_ROOT> --action <ID>`（或 `--keyword`；加 `--endpoint` 抽真实地址；`--out contract.md` 落盘；`--kb` 可省略，默认回退到与 skill 同级目录的 `qa-req2testcase-generator/user_knowledge`） |
| B 本地文件 | 用户给的绝对路径 `.md/.txt/.csv/.json` | 用 Read 工具直接读取 |
| C 粘贴正文 | 用户直接贴入对话 | 直接采用对话中的文档文本 |
| D 在线 URL | showdoc / Swagger / 开放平台文档页 | WebFetch `<URL>`（公开 showdoc 链接通常可抓；需登录的页面可能拿不到，转 B/C 模式） |

> 无论哪种来源，审查对象必须是**文档原文**，不是接口实际返回。实际返回与文档不一致属于「文档与实现不一致」，是本文档 §5 的高价值产出之一，不是本模式直接判定的内容。

> 知识库常见位置：与本 skill 同级目录下的 `qa-req2testcase-generator/user_knowledge`（即 `<skill父目录>/qa-req2testcase-generator/user_knowledge`），可直接作为 `kb_load_contract.py` 的 `--kb` 参数值。

## 2. 审查清单（逐项打勾，命中问题挂到维度）

### 2.1 字段参数说明（请求 + 响应，逐字段）

对每个请求参数与响应字段，核对 7 要素是否齐备且准确：

| 要素 | 检查点 | 常见问题 | 挂维度 |
|---|---|---|---|
| **参数名称** | 拼写正确、无歧义、与响应 / 示例同名 | 名称错位、大小写 / 下划线混用 | K7 |
| **数据类型** | 明确标注（int/long/string/bool/array/object/enum/date…）；与示例、与响应实际类型一致 | 类型缺失、示例类型与声明不符 | B / K |
| **是否必填** | 明确标注 必填 / 可选；缺必填时的行为（报什么错码？）有说明 | 未标注、必填 / 可选自相矛盾 | B1 |
| **取值范围** | 数值上下限、字符串长度、枚举全集、数组元素约束；越界行为（报错 / 截断 / 兜底）有说明 | 范围缺失、枚举不全、越界未定义 | B2 / B3 |
| **默认值** | 区分「不传 / 传空 / 传 null」三种缺省；默认值标注且与取值范围兼容 | 默认值矛盾、缺省语义不清 | B9 |
| **单位** | 时间（含时区）、金额（币种）、数量、比率等注明单位 | 单位缺失引发歧义 | K |
| **示例** | 给出可运行示例；覆盖枚举 / 边界；与类型 / 范围 / 默认值自洽 | 示例缺失、示例与说明冲突 | K9 / B |
| **传输契约** | `Content-Type` / `Accept` / 编码 / 必要请求头是否明确；下载/上传/分页是否需要特殊头或幂等键 | 头部说明缺失、与正文语义不一致 | V / K |
| **认证生命周期** | token / 签名 / 时间窗 / 重放窗口 / 刷新与撤销规则是否说明完整 | 过期、刷新、撤销、重放窗口未说明 | A9 / A11 |

### 2.2 前后一致性

- 请求字段名 ↔ 响应字段名一致（避免「入参 `parentId` / 出参 `parent_id`」）。
- 文档多处（概述 / 参数表 / 响应示例 / 错误码）对同一字段描述一致。
- 跨接口字段命名风格统一（snake_case 或 camelCase 二选一，不混用）→ **K7**。
- 旧版客户端能否容忍新增 / 改名字段（向前兼容）→ **L2**。
- **展示型字段的 UI 描述**（K9 延伸，有对应页面的接口必查）：时间 / 金额 / 状态 / 枚举等会在页面上展示的字段，文档是否说明**页面展示格式与单位**（如"时间按用户时区展示，格式 YYYY-MM-DD HH:mm"、"金额单位分，页面展示两位小数元"）。缺失记「文档缺失（低）」——它是 AB3 展示口径 / AB5 默认值口径争议的源头（页面基线登记见 `ui_baseline.md`）。

### 2.3 错误码与错误信息

- 是否完整列出**所有可能**错误码（请求级 / 业务级 / 系统级）。
- **错误码 ↔ 文案映射一致**：同一码在不同路径下文案一致；文档声明码的实际文案须吻合；出现**未声明码**（如 `999`）记缺陷 → **H9**。
- 区分 **HTTP 状态码**（401/403/404/409/429/5xx）与**业务错误码**，且语义一致（见 framework §9.7）。
- 错误信息**根因不掩盖**：不同成因给不同信息，无未渲染占位（`Email[]`、`{0}`）→ **H6**。
- 错误码是否随接口版本演进有弃用 / 新增说明。

### 2.4 边界条件

- 空值 / 空串 / `null`、超长、越界、特殊字符、emoji、注入串。
- 分页边界（**AA**）：`page`/`pageSize` 为负 / 零 / 超大、越界页码返回、总数计算、排序字段非法。
- 数值 / 字符串 / 数组边界；并发（同资源并发写）是否说明。
- 时间边界：闰年 / 跨时区 / 夏令时（国际版尤其，见 §1.3）。

### 2.5 字段间依赖关系

- **条件必填**：如 `type=A` 时 `fieldX` 必填，否则可选——文档须明示。
- **互斥字段**：如 `share_type=link` 时 `password` 无效。
- **联动 / 默认值依赖**：某字段值决定另一字段可选性 / 默认值。
- **组合约束**：多字段联合校验规则（如起止时间关系、总额与明细一致性）。
- 以上若文档未说明，记为「依赖关系缺失」，优先级高（最易引发实现歧义，且测试时无法判定哪边对）。

### 2.6 歧义 / 缺失 / 不合理（综合体检）

- **模糊措辞**：「一般」「通常」「可能」「视情况」等无判定标准的表述。
- **缺失**：必填 / 类型 / 范围 / 单位 / 示例任一项空白。
- **矛盾**：示例与说明冲突、两处描述不一致。
- **不合理**：默认值越界、枚举含非法值、错误码复用语义冲突、必填字段却无示例。

## 3. 严重度与问题台账（复用 9 列格式）

沿用 `references/issue_format.md` 的 9 列结构：

```
编号 | 类型 | 严重程度 | 状态 | 维度 | 问题描述(现象化) | 请求Body | 预期结果 | 实际结果
```

- **类型**：缺陷（子类标注 **文档缺陷** / **文档与实现不一致** / **文档歧义** / **文档缺失**）；或 建议项 / 文案优化。
- 本模式不实际发请求，**请求 Body / 预期 / 实际** 三列可留空，或填「文档原文片段」；重点在「问题描述」列现象化描述文档问题（例：「文档说 `include` 为 int，但示例里填的是字符串 `"1"`」）。
- **维度**：挂到对应维度编号（B8 / K7 / H9 / AA3 / L2 …），便于按维度统计、反哺 `defect_patterns.md`。
- **严重程度**：高（矛盾 / 缺失致实现歧义）、中（示例冲突 / 单位缺失）、低（措辞模糊 / 建议项）。

## 4. 输出物

- `api_test_doc_review_report.md`：审查结论 + 逐项清单结果 + 问题汇总。
- `api_test_doc_issues.csv`：9 列问题台账（utf-8-sig 逗号分隔；模板见 `assets/issue_template.csv`）。

## 5. 文档审查 vs 接口测试的关系

- **纯文档缺陷**（示例缺失、措辞模糊、单位遗漏）：反馈文档 owner 修正，不直接判接口缺陷。
- **文档与实现不一致**（文档说必填实际可选、示例字段名与实际不符）：高价值——要么文档错、要么实现错，需拉实现核对，记「需求确认」转测试。
- 文档审查发现的问题，应在后续接口测试中作为**优先验证项**（文档说 A、实现疑似 B → 用例重点打 A 是否真成立），形成「审文档 → 测实现」的闭环。

> 提示：本模式发现的「文档与实现不一致」问题，正是 `defect_patterns.md` 中「文档与实现不一致」缺陷子类的主要来源，审查时可直接归入该子类统计。
