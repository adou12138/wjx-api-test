# 接口冒烟模式（广度优先）

## 一、它和深度测试的分工

同一个 skill 里的两条路径，回答的是两个不同的问题，**不要混用**：

| | 冒烟模式 | 深度测试模式 |
| --- | --- | --- |
| 覆盖方式 | 广度优先：一批接口全跑一遍 | 深度优先：单接口按 31 类维度挖透 |
| 回答的问题 | 每个接口**基本调用通不通** | 这个接口在各类输入下**行为对不对** |
| 断言强度 | 只看业务成功与否（result） | 收紧断言：契约、错误关键词、HTTP 语义、过度校验 |
| 产出 | 批量可用性清单 + 失败项 | 逐条缺陷台账（含复现报文） |
| 适用场景 | 环境巡检、版本回归、新环境验收 | 指定接口的详细测试 |

**配合方式**：先跑冒烟圈出「不通」的接口，再对失败项转深度测试定位根因。冒烟不替代深度测试，反之亦然。

## 二、三份外部资产

引擎（`scripts/smoke_runner.py`）本身零业务知识，一切通过三份资产注入：

| 资产 | 作用 | 是否含业务知识 |
| --- | --- | --- |
| `--config` 环境配置 JSON | 地址模板、公共参数、账号、QPS 档位、判定关键词、专项覆盖参数 | 是（环境层） |
| `--cases` 案例清单 JSON | 每个接口的 action、模块、端点、限流档、参数模板、依赖声明 | 是（接口层） |
| `--hooks` 业务适配层 PY（可选） | 只有无法用数据表达的动作：环境准备、资源登记、收尾清理 | 是（编排层） |

引擎负责：加载、按顺序执行、渲染参数、发请求、判定、提取上下文、节流、出报告。

**请求超时**：默认取配置 `timeout`（缺省 60 秒），命令行 `--timeout <秒>` 可覆盖它——用于临时放宽慢接口的等待，或收紧以更快暴露挂起。只影响单次请求等待时长，不改判定规则。

## 三、案例字段

```json
{
  "action": "1001007",
  "name": "2.2.7 修改答卷[1001007]",
  "module": "答卷[1001]",
  "endpoint": "default.aspx",
  "qps": 10,
  "na_hints": [],
  "contract_file": "开放接口文档/答卷[1001]/044_2.2.7 修改答卷[1001007].md",

  "generate": { "usersystem_uid_run": "api${uuid8}" },
  "pre": [
    { "action": "1001001",
      "params":  { "vid": "${env.modify_vid}", "submitdata": "${env.modify_submitdata}" },
      "extracts": { "modify_jid": "data.joinid" },
      "retry_until": { "path": "data.joinid", "max": 5, "sleep": 0.5 } }
  ],
  "skip_if": "!ctx.modify_jid",
  "params":  { "vid": "${env.modify_vid}", "jid": "${ctx.modify_jid}" },
  "extracts": { "last_jid": "data.jid" }
}
```

| 字段 | 说明 |
| --- | --- |
| `action` / `name` / `module` | 标识与分组，module 用于汇总报告归类 |
| `contract_file` | 该接口契约文档的相对路径。**当前引擎不读取该键，仅作人工关联参考，不会被自动校验**——引擎的全部输入是 config / cases / hooks 三份资产 |
| `endpoint` | 子网关名，替换配置 `base_url` 里的 `{endpoint}` 占位 |
| `qps` | 限流档位，对应配置 `qps_tiers` 里的间隔秒数 |
| `na_hints` | 该接口专属的 N/A 关键词，追加在全局 `na_keywords` 之后 |
| `generate` | 生成本次运行的一次性标识并存入上下文（子账号名、成员 ID 等），已存在则不覆盖 |
| `pre` | 前置步骤列表：先调某接口并把响应里的值提取进上下文，供本例使用 |
| `pre[].retry_until` | 轮询直到指定路径有值——用于「创建后需等待才能查到」的最终一致性场景 |
| `skip_if` | 条件跳过。**在 `pre` 与 `generate` 之后评估**，因为前置步骤可能正是为了满足该条件 |
| `params` | 请求参数模板 |
| `extracts` | 从响应提取值进上下文，供后续依赖接口使用 |

### 占位符

| 写法 | 取值 |
| --- | --- |
| `${ctx.键}` | 上下文值（bootstrap 设置、`extracts` 提取、`generate` 生成） |
| `${env.键}` | 配置里的专项覆盖参数（`overrides`） |
| `${run_id}` | 本次运行标识 |
| `${ts}` | Unix 秒级时间戳 |
| `${uuid8}` / `${uuid10}` | 随机十六进制串 |
| `${rand:30-100}` | 30–100 的随机整数 |

### skip_if 语法

只支持三种简单形式，不给案例文件引入脚本能力：

- `ctx.键` —— 键为真值则跳过
- `!ctx.键` —— 键为假值则跳过
- `ctx.键 == 值` —— 相等则跳过（`env.键` 同理）

## 四、四级判定

判定按顺序短路，**顺序不能变**：

1. **ERROR** —— 网络或环境异常（连接失败、超时、响应非 JSON、命中 `env_keywords`）。重试 `error_retry` 次后仍异常才落 ERROR。**不计入缺陷**。
2. **PASS** —— 业务成功（`result=true`）。
3. **N/A** —— 业务失败但错误信息命中 `na_keywords` 或该接口的 `na_hints`。**不计入缺陷**。
4. **FAIL** —— 业务失败且无法归因于环境限制。**计入问题台账**。

问题台账只收录 FAIL 与 ERROR 两类，且两者分开标注（缺陷 / 环境），避免把环境抖动当缺陷报给开发。

### N/A 关键词的两条纪律

- **先验证再收录**：一个关键词只有在确认「该模块在本环境确实未开通/已废弃」后才加入。看到报错就加关键词，等于自我屏蔽缺陷。
- **定期复查**：环境开通后，对应关键词必须移除，否则该模块的真实缺陷会被永久判成 N/A。

> 已踩过的坑：把「通讯录」「用户体系」这类**模块名**直接作为 N/A 关键词，会让这两个模块的所有报错都被判成环境限制，真缺陷也被吞掉。宁可用具体文案（如「未开通通讯录」「非通讯录企业」），不要用模块名。

## 五、执行前检查清单

1. 配置里的地址、公共参数、账号与**用户指定的环境**一致（不写死默认域名）
2. `qps_tiers` 与被测环境真实限流匹配，否则会被限流打成 ERROR 假象
3. `teardown_enabled` 确认为 `false` 再开跑；确认目标为测试环境后才置 `true`
4. 先用 `--dry-run` 过一遍，确认参数渲染无异常、无语法错误
5. 大批量前先用 `--only <单个action>` 试跑一个，验证连通性

## 六、清理与授权

删除是不可逆操作。适配层的 `teardown` 默认**不删数据**，只在 `teardown_enabled=true` 时执行：

- 只清理本次运行登记的资源（`ctx.created_vids`），不碰环境里原有的数据
- 清理失败不中断整体流程，逐条记录结果
- 开启前必须确认：目标为测试环境、清单中的 ID 均为本次创建

## 七、接入一个新项目

1. 复制配置模板，改 `base_url`、`common_params`、`account`、`qps_tiers`
2. 按依赖顺序写案例清单：先写无依赖的查询类，再写创建类，最后写删除类
3. 复杂依赖用 `pre` + `retry_until` 表达，简单参数直接写 `params`
4. 只有确实无法用数据表达时，才写适配层（通常只需要 `bootstrap`）
5. `--dry-run` 验证 → `--only` 单跑 → 全量跑

## 八、已知边界

- 引擎按 `result` 字段判定成功，假设响应是 `{result, data, errmsg}` 结构。结构不同的接口需改配置里的判定字段名（当前硬编码在 `classify()`，如需支持可在配置里加 `result_field` / `error_field`）
- `extracts` 只支持点号路径与列表下标，不支持按条件筛选（如「取 name=xxx 的那条」）。需要筛选时改用适配层
- 冒烟不做并发、不做数据量压力、不做安全测试，这些属深度测试与专项测试范畴
- 流式 / 长连接接口不在冒烟模式的主覆盖范围内，应走协议专项或深度测试路径
- 认证生命周期、请求头/传输契约、文件完整性、可观测性与复现链路属于深度测试补强项；冒烟只做最小可用性验证，不承担这些专项断言
