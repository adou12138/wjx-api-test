# 通用接口测试维度与场景设计框架

> 用途：本文档是一套**接口测试设计方法论 + 可填写模板**，用于指导对**任意 HTTP / OpenAPI / GraphQL / gRPC / WebSocket 接口**进行测试设计（测试策划、维度覆盖、场景推导），不绑定任何具体业务。
> **总原则**：先判适用性，再做维度覆盖；先做断言分层，再做结果判定；先看契约与状态，再看业务结果。
> 适用：对外/对内 REST、类 RPC（单 POST + JSON Body 的网关动作）、网关透传、GraphQL、gRPC、WebSocket。
> 定位：测试**设计**框架，产出"测什么 / 怎么测 / 怎么判定"，**不替代具体用例脚本**；具体用例按本框架第 3 节模板落地。
> 来源：由问卷星 AI 主页接口（1000107/1000108）实测复盘抽象而来，已去除业务耦合。

## 0. 如何使用本框架（接入一个新接口的 8 步）
| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | **梳理接口契约**：动作/路径/方法、必填与可选参数、类型、枚举取值、长度/数值边界、响应结构（成功/失败字段） | 接口信息表（见 §9.1） |
| 2 | **识别协议类型**：RESTful / GraphQL / gRPC / WebSocket，按 §1.1 速查表追加该协议的专属测试重点 | 协议差异补充清单 |
| 3 | **标注鉴权模型**：签名/Token/APIKey/AppID/子账号体系，哪些参数参与鉴权 | 鉴权说明 |
| 4 | **标注状态机**：被测对象（如"主页/订单/资源"）的生命周期：创建 → 发布/启用 → 暂停/禁用 → 更新 → 删除/下线 | 状态转换图 |
| 4.5 | **适用性判断**：先读 `applicability_matrix.md`，按五步法确定接口业务域与操作类型、**是否国际版场景**，筛选适用维度，标注 N/A | applicability_matrix.md §0–§7 |
| 4.6 | **过一遍高频缺陷清单**：读 `defect_patterns.md`，逐条确认本接口是否可能命中，命中的转成用例 | 启发式检查表勾选结果 |
| 5 | **维度归类**：把每个接口套入 §2 的 **30 大类**（A–L 通用 + M–Z 业务域专项 + AA–AD 通用补充），逐类判定覆盖状态（强 / 部分 / 缺口 / 排除 / N/A）。国际版维度默认标 N/A | 覆盖率矩阵（§4 模板） |
| 6 | **推导场景**：按 §3 三要素模板，为每个"缺口/部分"维度编写场景描述 | 场景清单（先设计、后实现） |
| 7 | **分层排优先级**：按 §5 依赖与风险分层，低依赖环境优先、特定账户环境靠后；按 §1.2 校验用例数是否达深度配额 | 执行路线图 |
| 8 | **（可选）预留 ENV 区**：仅在做了多环境对比、且观察到环境行为不一致时，记录差异以避免误判为缺陷或漏报；默认只在单一指定环境测试，此步可跳过 | 环境差异台账（可选） |
> 关键原则：**先设计、后执行**。本框架的输出是"设计"，用例脚本/手动步骤是"实现"，二者分离。

## 0.1 测试环境分类与配置（按环境类别记录固定参数）

> 约定：把"固定参数（编码/签名/AppID/账号）"集中登记，避免散落在各份用例里、也便于核对不错配。
> **默认只在用户当前指定的那一个环境测试，不需要列举所有环境类别**。下面以问卷星 AI 主页接口（1000107/1000108）实测为例登记；换接口时复制本节、替换值即可（只填要测的那一个环境即可）。

### 环境类别划分
- **本地环境类**：团队内自建 / 内网穿透的测试服务（示例）。本框架**不要求**把本地/预发布/生产全部登记——只登记当前要测的那一个环境即可；若确实跨环境对比、且出现规则/文案不一致，差异记 ENV 台账，不擅判缺陷。
  - `本地实例A` —— `https://<域名A>`（appid <APPID>，主账号 <主账号> / 子账号 <子账号>）
  - `本地实例B` —— 同一台服务器的两个域名：`https://<域名B1>` 与 `https://<域名B2>/openapi/default.aspx`（appid <APPID>，主账号 <主账号> / 子账号 <子账号>）；两者指向同一后端，任选其一即可。若某域名曾出现全路径 404 的可达性问题，换用同后端的其他域名。
- **预发布环境类**：接近生产、鉴权/内容安全更完整，但可能有防重提交、限流等旁路机制，需绕过干扰才能稳定判定。
  - `预发布实例` —— `https://<域名>/openapi/default.aspx`（appid <APPID>，主账号 <主账号> / 子账号 <子账号>）

### 按类别登记的固定参数模板
```
【本地环境类 · <APPID>】实例A / 实例B
  BaseURL : https://<域名A>   （实例B 改 https://<域名B2>/openapi/default.aspx）
  路径    : /openapi/default.aspx        方法: POST   encode: sha1
  appid   : <APPID>
  sign    : 1234        （按用户要求不校验）
  主账号  : <主账号>      子账号: <子账号>

【预发布环境类 · <APPID>】预发布实例
  BaseURL : https://<域名>
  路径    : /openapi/default.aspx        方法: POST   encode: sha1
  appid   : <APPID>
  sign    : 1234        （按用户要求不校验；注意：若实测错误 sign 仍创建成功→鉴权疑似未校验，见 A1）
  主账号  : <主账号>   子账号: <子账号>
```

> 登记要点：
> - 分类维度优先用"环境性质"（本地 / 预发布 / 生产），同性质多实例归一类，差异在备注列明。
> - 账号随"环境类别 + appid"成对记录，主/子账号一并写，避免混用导致越权类用例判错。
> - 签名若约定"不校验"，显式标注，并在对应鉴权维度（A）用例里验证"是否真的未校验"（如 devtest 的 A1 发现）。
> - 本地类端点失效/切换时，只改 BaseURL，其余固定参数（encode/appid/sign/账号）不变。

## 1. 通用测试维度总览（30 大类：A–L 通用 + M–Z 业务域专项 + AA–AD 通用补充）

对任一接口，从这些维度审视覆盖，避免出现"只测了主链路、其余全盲"的情况。
> 编号说明：A–L 为通用维度；M–Z 为业务域专项（按需，见 `applicability_matrix.md`）；AA–AD 为通用补充维度（分页 / 前后端口径 / 幂等唯一性 / 事件回调）。国际版专属维度集中在 §1.3，默认不适用。
| 维度 | 名称 | 关注点 | 典型"假通过"盲区 |
|---|---|---|---|
| A | 鉴权与权限 | 签名/Token/账号合法性、越权、授权范围、认证生命周期、mTLS、传输契约 | 只验"能调用"，不验"该账号是否越权" |
| B | 参数校验 | 必填缺失、类型错误、枚举越界、长度/数值边界 | 只验"不报错"，不验"是否被正确处理"；**更隐蔽：把"非法输入应被拒绝"误断言成"应当成功"，导致宽松接口全判通过** |
| C | 字段语义真值 | 写入的数据是否**真落库/真生效**（更新后读回验证） | 只验 `result=true` + 字段非空，**从不回读验证** |
| D | 业务主链路 | 核心创建/查询/更新/删除流程、关键分支、接口串联 | 只覆盖主成功路径，漏异常分支与依赖链 |
| E | 状态机与生命周期 | 合法状态转换、非法转换、终态操作 | 只测单步，不测完整链路与非法跳转 |
| F | 组合与交叉 | 多字段同时变异、因子组合矩阵 | 永远单字段变异，漏交互缺陷 |
| G | 安全深化 | 注入、越权、SSRF、重放、信息泄露、脱敏 | 只防已知攻击，漏业务逻辑型安全 |
| H | 错误处理质量 | 错误码/文案具体性、是否 500、是否泄露堆栈 | 只验"失败"，不验"报错是否可定位" |
| I | 编码与国际化 | 特殊字符、emoji、多语言、空字节、BOM | 用 ASCII 跑完就当全覆盖 |
| J | 性能与稳定性 | 时延、并发正确性、限流、超时、重试退避、降级熔断 | 单用户串行，漏并发竞争与故障容错 |
| **K** | **契约测试** | 请求/响应结构、字段类型、必填性、契约版本与 CI | 只测"接口能通"，不测"结构是否悄悄漂移" |
| **L** | **兼容性测试** | 向后/向前兼容、协议与序列化、上游与中间件、客户端 SDK | 只测新版本，旧客户端解析直接崩 |
| **M** | **资源导出/下载** | download_url、导出选项、数据口径、链接有效期、空数据 | 只验"能下载"，不验导出内容正确性与链接时效 |
| **N** | **层级资源管理** | 层级上限、父级只读、树形返回、管理员三态、自定义字段 | 只验 CRUD，不验层级约束与状态机 |
| **O** | **异步通知/发送** | 定时时区、列表字段、重发枚举、提醒参数、渠道枚举 | 只验"发送成功"，不验时区与字段完整 |
| **P** | **分享/链接参数** | 渠道状态枚举、状态联动、参数去重、分享方式 | 只验"能分享"，不验状态联动与参数校验 |
| **Q** | **多角色关系管理** | 自评一致性、级别数量、覆盖语义、已有数据限制 | 只验"能创建关系"，不验业务规则约束 |
| **R** | **报告/结果分享** | 报告类型、分享条件、互斥、密码 | 只验"能分享"，不验类型与条件约束 |
| **S** | **容器/分类管理** | 归属校验、query_all、共享权限、层级口径 | 只验"能建容器"，不验归属与共享 |
| **T** | **账号/身份信息** | 字段完整、状态同步、命名规范 | 只验"能查用户"，不验字段完整与同步 |
| **U** | **批量数据导入** | 数据合法性分级、部分成功、错误定位 | 只验"导入成功"，不验非法数据处理与部分成功 |
| **V** | **请求标识与追踪** | X-Request-Id 唯一性、与签名关系、重复使用 | 从不验证请求头标识 |
| **W** | **文件/附件管理** | 附件字段、签名题、链接有效期、类型限制 | 只验"能上传"，不验附件字段与时效 |
| **X** | **批量操作** | 部分成功语义、失败明细、删除数量、与事件联动 | 只验"批量成功"，不验部分失败处理 |
| **Y** | **复杂结构返回** | 各子类型返回结构、选项属性、嵌套完整 | 只验"有数据"，不验各子类型结构完整 |
| **Z** | **国际化/多语言** | 语言枚举、多语言标题、批量部分成功、翻译完整 | 只用中文测，不验多语言与枚举 |
| **AA** | **分页与列表查询** | 页码/条数边界、游标/Token 翻页、总数一致、排序稳定、筛选生效、空结果 | 只验"能返回数据"，不验分页边界、游标稳定性与筛选是否真生效 |
| **AE** | **认证/传输补充** | 认证生命周期、请求头/传输契约、mTLS、重放时间窗 | 只测 body，不看 header / token 生命周期 / 传输语义 |
| **AB** | **前端-接口口径一致** | 权限口径、校验口径、展示口径、枚举口径、默认值口径 | 只测接口自身，从不与页面基线比对（历史缺陷第二高发模式） |
| **AC** | **幂等与业务唯一性** | 重复请求幂等、业务唯一性、列表去重、冲突值回显 | 只测"能创建"，不测重复提交与唯一性冲突 |
| **AD** | **事件与回调** | 事件完备、不重不漏、载荷准确、订阅范围、重试补推 | 只测"Webhook 创建成功"，不测事件是否真推送 |
> 标注约定：**强**（已系统覆盖）/ **部分**（覆盖但断言弱或有缺口）/ **缺口**（基本没测）/ **排除**（本次范围外，须显式声明）。
> **说明**：M–Z 为业务域专项维度，**不是每个接口都适用**。使用前必须先读 `applicability_matrix.md` 判断接口业务域与操作类型，只取适用的专项；不适用的标注 N/A。例如创建资源接口不适用 M（导出下载）。
> **AA–AD 为通用补充维度**：AA 适用所有列表类接口；AB 适用所有有对应页面的接口；AC 适用所有写接口；AD 适用所有会触发事件/回调的接口。
> **国际版维度默认不适用**：Z（多语言）及其国际版扩展（见 §1.3）在国内版测试中**一律标 N/A**，仅当满足 §1.3 启用条件时才加载。

## 1.1 协议差异化测试重点速查 

不同协议的失效模式差异很大，套用维度前先按协议追加专属重点：
| 接口类型 | 典型代表 | 测试重点 | 协议特点（决定了哪些维度要加权） |
|---|---|---|---|
| **RESTful** | CRUD API、微服务接口 | 状态码语义、HTTP 方法语义（GET 幂等 / POST 非幂等）、RESTful 规范符合度 | 无状态、资源导向、可缓存 → **A 鉴权、B 参数、C 真值、K 契约** 为主 |
| **GraphQL** | 聚合查询、数据中台 | **查询复杂度/深度攻击**、**N+1 问题**、字段级权限细粒度、批量查询限流 | 单一端点、按需查询 → **G 安全（查询深度）、J 性能（N+1）、A 授权（字段级）** 加权 |
| **gRPC** | 内部服务通信、高吞吐 | 消息格式（Protobuf 兼容）、**流处理**（双向流/断流重连）、超时重试、错误码映射 | Protobuf、双向流、高性能 → **L 兼容（Schema 演进）、J 稳定性（流/超时）** 加权 |
| **WebSocket** | 实时推送、消息通知 | **连接管理**（重连/心跳/断线）、**消息顺序与丢失**、并发连接数、订阅鉴权 | 长连接、全双工、有状态 → **J 稳定性（连接）、A 鉴权（订阅态）、E 状态机（连接生命周期）** 加权 |
> 用法：先按 12 维通用覆盖，再按上表给该协议"加权维度"追加深度场景，避免用 REST 的思维测 gRPC/WS 而漏掉流式与连接态缺陷。

## 1.2 测试深度与用例数配额 

避免"测了但深度不够"，按接口复杂度设定用例数下限：
| 复杂度 | 用例数要求 | 说明 |
|---|---|---|
| 简单接口 | 接口数 × 5 | 单一功能、参数少 |
| 中等接口 | 接口数 × 10 | 多参数接口 |
| 复杂接口 | 接口数 × 15 | 多依赖 / 多状态接口 | **最低覆盖红线**：无论复杂度，至少覆盖 **功能验证 / 参数组合 / 安全鉴权** 三个维度（对应 D+B+F、B、A+G）。

**各维度用例配比参考**（与维度编号的映射）：
| 配比来源 | 占比 | 对应本框架维度 |
|---|---|---|
| 功能 | 35% | B 参数 + C 真值 + D 主链 + E 状态机 + F 组合 |
| 安全 | 18% | A 鉴权 + G 安全 |
| 异常 | 15% | H 错误处理 + J（超时/重试/降级/熔断/数据异常） |
| 契约与口径 | 12% | K 契约 + **AA 分页 + AB 前端一致性** |
| 幂等与事件 | 10% | **AC 幂等唯一性 + AD 事件回调** |

## 1.3 国际版（i18n / l10n）扩展维度 —— 默认不适用

> **默认：国内版测试不加载本节任何维度，全部标 N/A。**
> 本节只在被测接口属于**国际版 / 海外站 / 多语言 / 跨币种**场景时启用。

**启用条件（满足任一即加载，否则标 N/A）**
1. 用户明确说明测的是国际版 / 海外版 / 多语言站点；
2. 接口文档或响应中出现 `language` / `locale` / `currency` / `timezone` / `tz` / `i18n` 字段；
3. 被测环境域名为海外站点，或账号归属海外区域；
4. 接口涉及金额、跨时区时间、多语言文案中的任一项。

**未启用时的处理**：在覆盖率矩阵（§4）中把 Z 与本节所有编号统一标注 `N/A（非国际版）`，**不计入通过率**。

### Z. 多语言（国际版专项）
- **Z1 语言枚举**：language 枚举值完整，native_name 返回正确；系统默认语种与自定义语种行为一致。
- **Z2 多语言标题**：新增/修改多语言标题生效，回查一致；**修改自定义语种时不得误改源语种**。
- **Z3 批量部分成功**：批量修改多语言标题时，一项失败不应导致全部失败（联动 X1）。
- **Z4 翻译完整**：多语言文案翻译完整，无遗漏。
- **Z5 语言版本字段**：langv 等语言版本字段返回正确。
- **Z6 时区一致性**：所有时间字段按用户时区转换；请求时间应接受带时区标记（`Z` / `+08:00`）；同一时刻在列表与详情中的显示一致；**至少覆盖 UTC / +08:00 / -05:00 三个时区各验一遍**。
- **Z7 本地化格式**：日期格式、数字千分位、小数点、货币符号、姓名顺序随 locale 变化；未指定 locale 时有明确默认。
- **Z8 多币种**：金额精度与最小单位（分 vs 元）、舍入规则、ISO 4217 代码与符号一致、汇率快照是否锁定、不支持的币种传入应被拒绝（禁止静默按默认币种处理）、金额不接受负数/科学计数法/精度溢出。

### H8. 错误信息国际化（国际版专项）
错误信息语言随请求语言 / `Accept-Language` 变化；中文环境不返英文、英文环境不返中文；禁止中英混排。

### I6–I9. 国际化编码（国际版专项）
- **I6 RTL 双向文字**：阿拉伯语 / 希伯来语等从右向左文字的存储与回显。
- **I7 组合 emoji**：ZWJ 序列（👨‍👩‍👧）、肤色修饰符、变体选择符不被截断。
- **I8 CJK 四字节字符**：罕见汉字、和制汉字、韩文古字按字符（非字节）计长。
- **I9 URL 保留字符**：`? # & = / + %` 在参数与内容中的转义一致性。

### 国际版专属陷阱
- **时区基线必须来自页面**：接口返回的时间值若与页面显示差固定小时数（典型 8 小时），即为时区未转换缺陷，不要归为 ENV。
- **金额不能只断言非空**：必须断言精度、币种与舍入，跨币种换算需可复现。

## 2. 逐维度场景族（可裁剪、可扩展）

下面每个维度给出**通用场景族**（不依赖具体接口）。实际使用时，把"对象/字段名"替换成你的接口参数。


### A. 鉴权与权限
- A1 **凭证缺失/错误**：不传签名/Token、传错值、传空 → 应被拒且提示明确。
- A2 **凭证篡改**：改 AppID/账号主体、用 A 的凭证调 B 的资源 → 越权应被拒。
- A3 **子账号/角色矩阵**：不同角色（管理员/普通/只读）调同一接口，验证最小权限原则。
- A4 **授权范围**：新开通的接口/动作是否自动获得权限，或需单独授权（业务规则验证）。
- A5 **配额/点数**：写类接口是否按规则扣减配额，未配置时行为是否定义清晰。
- A6 **越权细分（横向/纵向）** ：横向=同角色改他人资源；纵向=低权限调高权限接口。两者必须分开设计。
- A7 **认证绕过与会话安全** ：Token 伪造/篡改、Session 固定、登出后 Token 是否失效、Token 续期与并发登录行为。
- A8 **频率配额与防刷** ：短时间高频调用是否触发防刷；与 J3 限流的区别是——A8 关注"身份维度"的配额，J3 关注"接口维度"的阈值。
- A9 **认证生命周期与时间窗** ：token 过期、刷新、撤销、多端登录后的旧 token 失效、签名时间戳误差、nonce 过期、重放窗口容忍区间。
- A10 **双向证书 / mTLS** ：若接口涉及双向证书或服务端证书校验，需验证证书链、证书过期、证书替换后的可达性与拒绝语义。

> **A 维度按「身份 × 操作面」成矩阵测，不要只测一条签名错误**。身份轴：主账号（对照）/ 子账号 / 跨企业 appid / 跨企业+主账号（双重矛盾）；操作面：写（本接口）/ 读（配套读接口）。
> **读面必须配对判定**：先用本企业身份自证读得到，再看跨企业身份能否读到。直接断言"跨企业读被拒"是假的通过——读接口常常因为缺必填参数而失败，那种失败与越权无关。
> 生成器已按此矩阵铺开；身份用 `<跨企业appid>` / `<子账号>` / `<主账号>` 占位符承载，配置缺项时点名跳过。`check=cross_tenant_read` 承担配对判定。
- A11 **请求头/传输契约** ：Content-Type、Accept、charset、gzip、idempotency-key、trace-id、correlation-id 等传输层契约是否明确、稳定且与错误/重试语义一致；下载/上传/分页/幂等类接口尤其要测。

### B. 参数校验

> **⚠️ 断言方向铁律（B 维度最常见、最隐蔽的盲区，实测踩过）**：
> B 维度的核心断言是 **"非法 / 缺失 / 类型错误 / 枚举越界 输入 → 应被【拒绝】"**。
> - 若接口**拒绝**（result=false）→ 校验生效，✅ PASS。
> - 若接口**接受**并返回成功（result=true）→ 这是**参数校验缺失缺陷**（应记问题单，**绝不是"测试通过"**）。
> - **严禁**用"期望成功"的用例去测非法输入（即把 `expect_success=True` 配给非法输入）。那样当宽松接口接受非法值时用例判 PASS，缺陷被完全掩盖——1006001 接口（查询文件夹）就因此漏报了 5 条参数校验缺陷。
> - 正确做法：非法/缺失输入一律用"期望被拒绝"的断言。运行器已封装 `assert_validation()`（见 `scripts/api_test_runner.py`），专用于此方向，避免写反。
> - 仅当产品**明确约定**"某非法枚举有文档化默认值/容错"时，才允许接受；此时须在问题单记为「符合预期/已确认非问题」并附产品确认，而非静默判通过。

- B1 **必填缺失**：逐个移除必填项（断言**应被拒绝 result=false**）；若仍返回成功=必填未生效缺陷。报错须指明缺失项（而非笼统"参数不足"）。
- B2 **类型错误**：字符串传数字、数字传字符串、布尔传字符串、传 `1.5`/非 int → **断言应被拒绝**；若接受=类型校验缺失缺陷。仅在产品明确约定"隐式转换"时才接受。
- B3 **枚举越界**：传不存在的枚举值（如 `2`/`999`）→ **断言应被拒绝**（命中文档化允许值提示）；若接受=枚举校验缺失缺陷。文档化默认值/容错属例外，须附产品确认记为「符合预期」。
- B4 **长度/数值边界**：等于上/下限、超上限、负数、0、极大值。
- B5 **格式非法**：邮箱/URL/手机号等格式校验（若字段有格式语义）。
- B6 **报文畸形**：非 JSON、缺字段、多字段、类型嵌套错误 → 应优雅报错不 500。
- B7 **参数污染与重复传参** ：同名参数传多次、参数名大小写变异、多余未知参数 → 行为应定义（取首个/取末个/报错），不静默吞掉。
- B8 **过度校验（反向盲区，与 B1–B3 对称）** ：文档标注为**可选 / 可空**的字段，传 `null` / 空串 / 不传 → **应成功**；被拒即记缺陷。
  > 为什么单列：B1–B3 只织了"欠校验"的网（应拒绝却接受）。反向缺陷同样真实——合法输入被误拒，用例判 FAIL 后极易被人工归因为"需求就这样"，从而**静默漏报**。这是与"假通过"对称的**"假失败"盲区**。
  > 高发触发点：**读接口返回的结构直接回写给写接口**（如"获取外观设置 → 保存外观设置"）必须能成功，写接口若对可空字段强制必填即为缺陷。
  > 断言 helper：`assert_no_over_validation()`。
- B9 **空值四态语义** ：对每个可选字段，区分 `字段缺失` / `null` / `""` / `[]` 四种形态，四态行为须文档化且互相一致。
  > 典型缺陷：非必填的手机号传 `""` 报格式错误（应为通过）；内容字段传空串竟创建成功（应提示必填）。
  > 断言 helper：`check_null_triad()`。

### C. 字段语义真值（最核心、最易被漏）
- C1 **写入真值回读**：创建/更新后，通过**独立查询接口**（详情/列表/统计）验证数据**确实落库且一致**（不只看响应 success）。辅助接口选择见 §9.4.2 矩阵。
- C2 **部分更新保留性**：只传部分字段更新，验证未传字段**保留原值**（而非被清空/重置）。
- C3 **字段优先级冲突**：当接口存在"同义字段"（如 `html` 与 `html_content`）同时传入且取值不同，验证以谁为准、是否报警。
- C4 **响应字段语义有效**：响应里的 URL/ID/状态确有业务含义（如返回的嵌入代码能正常渲染，而非裸脚本）。
- C5 **更新生效延迟/异步**：更新后是否需等待、是否有最终一致性窗口。
- C6 **DB 层真值核验（最强断言）** ：回读接口也可能"返回假成功"，必要时直接查库验证落库值（`DB: table.field = expectedValue WHERE condition`，见 §9.3）。
- C7 **跨字段联动副作用** ：修改字段 A 是否意外影响字段 B（如改类型清空内容、改状态重置配置）。

> **C 系列的推荐观测手段优先级**：DB 断言（C6）> 独立查询接口回读（C1，详见 §9.4.2 辅助验证矩阵）> 响应体字段（最弱，仅作辅助）。

### D. 业务主链路
- D1 **核心成功路径**：创建→查询→更新→删除（或等价动作）全链路通。
- D2 **典型用户路径**：模拟真实使用组合（如"未发布草稿 → 编辑 → 发布"）。
- D3 **关键分支**：默认回退（缺省标题/默认类型）、别名兼容、幂等（重复提交）。
- D4 **依赖前置**：更新/删除依赖对象处于某状态（如"已发布态需先暂停"）时的守卫逻辑。
- D5 **接口串联 / 依赖链** ：上一接口返回值作为本接口入参（如 `使用步骤N返回的 $.data.orderId 作为本步骤入参`）；前置条件须说明依赖接口的调用顺序。
- D6 **失败回滚与事务一致性** ：链路中某步失败时，前面已成功的步骤是否回滚 / 是否留下脏数据。

### E. 状态机与生命周期
- E1 **完整生命周期链路**：按下状态图逐状态转换，全部合法路径跑通。
- E2 **非法状态转换**：从终态/不兼容态发起操作 → 应被拒并提示。
- E3 **非法 state 值**：状态字段传越界值 → 应被拒。
- E4 **终态操作**：已删除/已下线的对象再更新/查询 → 行为应定义。
- E5 **并发状态跃迁** ：并发触发互斥转换（如同时"发布"与"删除"），验证不出现中间态/状态撕裂。
- E6 **重复操作提示语义** ：对终态或已处于目标态的对象**重复同一操作**（已删除再删、已发布再发、已暂停再暂停）→ 须返回明确提示（如"问卷已删除"），**禁止静默返回 true**。
  > 断言要点：不仅断言 `result`，还要断言错误信息中包含状态描述。
- E7 **非法前置态拦截** ：终态对象禁止后续变更操作（已删除对象禁止发布 / 暂停 / 更新），缺失拦截即为缺陷。
- E8 **转换矩阵实测** ：逐个目标状态提交并回读，产出「哪些被接受 / 被拒 / 回读值」的事实表。
  > 哪一对转换合法是业务语义，自动生成器不猜，所以矩阵**只产出事实、不判非法转换缺陷**；
  > 唯一能确定判的是「接受了但回读值 ≠ 提交值」——状态被静默改写或参数失效，`check=state_transition` 硬判这一条。

### F. 组合与交叉

> **断言方向提醒（因子矩阵盲区）**：因子矩阵**既要断言合法组合应成功，也要断言非法组合应被拒绝**。
> 只把结果"记录"下来（不判通过/失败）、或只对"本应成功却失败"记问题单，会导致"本应被拒绝却接受"的缺陷全部漏报——这正是 1006001 接口漏报 5 条参数校验缺陷的根因。
> 矩阵中**每个格的"预期结果"必须事先写明**（成功 / 拒绝），再比对实际；任何"实际接受但预期应拒绝"的格，一律记缺陷。

- F1 **因子矩阵**：对 2–3 个关键枚举做笛卡尔积（如 `类型 × 发布状态 × 账号角色`）；每格先写预期（成功或拒绝），再比对实际。
- F2 **边界组合**：超长内容 + 敏感词 + 特殊字符同时出现。
- F3 **异常叠加**：必填缺失 + 类型错误 同时发生，验证报错优先级与明确性。
- F4 **状态 × 权限交叉矩阵** ：不同状态的对象 × 不同角色操作，形成交叉表（最易暴露守卫逻辑漏洞）。

### G. 安全深化
- G1 **注入（代码/DOM）**：内容字段注入 `<script>`/事件处理器 → 验证被过滤/转义/拒绝（属**正确安全行为**，非缺陷）。
- G2 **内容安全（违禁/敏感词）**：title/正文含违规词 → 验证是否有内容审核（**常见缺口**：接口只防可执行代码，不防违规内容）。
- G3 **越权（横向/纵向）**：子账号改他人资源、普通账号调管理员接口。
- G4 **SSRF / 外链**：内容内含外部 URL/资源引用，验证是否被限制。
- G5 **重放攻击**：截获合法请求原样重发，验证是否有防重放（nonce/时间戳/一次性）。
- G6 **信息泄露**：错误响应是否泄露内部堆栈/SQL/路径/敏感配置。
- G7 **命令注入 / 模板注入** ：参数含 shell 元字符（`;|&$`）、模板语法（`{{}}`、`${}`）→ 验证不被执行。
- G8 **数据安全（加密与脱敏）** ：敏感字段（手机号/邮箱/身份证/密钥）在传输与响应中是否加密/脱敏，日志是否落明文。
- G9 **业务逻辑型安全** ：金额/数量/价格等关键业务字段在客户端可篡改时，服务端是否二次校验（区别于技术型注入，属"逻辑漏洞"）。

### H. 错误处理质量
- H1 **错误码规范**：失败响应有结构化错误码，非仅靠文案。
- H2 **文案具体性**：缺失参数时指明"缺少哪个参数"，非法枚举时指明允许值。
- H3 **不崩溃**：任何非法输入均返回受控 JSON 错误，不 500 / 不超时无限挂起。
- H4 **契约稳定**：成功/失败响应字段结构稳定，不随环境悄悄变化（ENV 风险）。
- H5 **重试一致性与幂等错误** ：同一错误请求重试多次，错误码/文案保持一致（不漂移）；写操作失败重试不产生副作用。
- H6 **根因不掩盖** ：错误信息须指向**真实**失败原因，禁止用笼统错误覆盖具体原因。
  > 典型缺陷：传错 roleId / 用户名 / 时间戳，一律提示"sign 验证失败"；缺少 appId 时也报"验签失败"——真实根因被掩盖，排查被彻底误导。
  > 测试法：**分别构造"凭证错误"与"参数缺失"两种请求，二者错误信息必须不同**；若相同即为根因掩盖缺陷。
  > 断言 helper：`check_error_root_cause()`。
- H7 **错误信息渲染完整性** ：错误信息中不得出现未渲染的模板占位（`{0}`、`%s`、`{{var}}`），变量必须已填充实际值。
  > 典型缺陷：邮箱重复时提示 `Email[]`，中括号为空——占位符未渲染，用户拿不到冲突值。
  > 断言 helper：`check_error_i18n()`（含占位检测）。
- H8 **错误信息国际化** ：见 §1.3 国际版扩展（国内版标 N/A）。
- H9 **错误码-文案映射一致** ：同一错误码在不同触发路径下文案一致；文档/映射表声明的每个错误码，实际返回文案须与声明吻合（关键短语命中）；出现映射表未声明的错误码记缺陷。
  > 典型缺陷：2003 错误码对应文案与实际请求不符（返回"The authorization token provided was invalid"但该码释义并非如此）；360 问卷不支持的题型返回未定义的 999 码。
  > 断言 helper：`check_error_code_mapping()`。

### I. 编码与国际化
- I1 **特殊字符**：¥、¤、emoji、引号、`<`、`&`、井号、@ 等是否被原样保存/正确处理（注意：部分字符如 `<` 可能被安全层转义而非截断）。
- I2 **控制/空字节**：内容含 `\x00` 等不可见字符是否被存储且下游正常。
- I3 **多语言/编码**：中文/日文/阿拉伯文混排、UTF-8 BOM 场景。
- I4 **超长编码**：接近上限的字符（非字节）长度处理。
- I5 **序列化格式兼容** ：JSON/XML/Protobuf 之间的编码差异（如 emoji 的 surrogate pair、大整数精度丢失）。

> 注：I5 与 L4 协议兼容互补——I5 关注"字符/数值编码正确性"，L4 关注"格式整体可解析"。
> 注：I6–I9（RTL 双向文字 / 组合 emoji / CJK 四字节字符 / URL 保留字符）属**国际版专项**，见 §1.3，国内版标 N/A。

### J. 性能与稳定性（按需，通常单独立项）
- J1 **响应时延基线**：单请求 P50/P95/P99。
- J2 **并发正确性**：N 并发更新同一对象，最终一致性/脏写判定（需有"读回"手段）。
- J3 **限流**：高频调用是否触发限流且返回明确错误（阈值、拒绝策略、恢复时间）。
  - **J3.1 配额归属口径** ：主账号 / 子账号 / 应用 / IP 各维度的配额是**共享还是独立**须文档明确并验证。典型缺陷：主账号与子账号分别请求时 tps 各为 10，未按"两者之和为 10"限制。
  - **J3.2 配置-实际一致性** ：配置的阈值与实测阈值必须一致。典型缺陷：配置 30 而压测实测不到 10。
  - **J3.3 限流响应语义** ：返回约定的状态码（429 或业务码）、含明确恢复时间提示、限流日志可查。
  - **J3.4 废弃配置项** ：配置列表中已失效的项应移除，避免误导使用者。
- J4 **超时行为** ：连接超时（TCP 建连）、读取超时（响应返回）、超时后的重试行为是否符合预期。
- J5 **重试与退避** ：重试间隔是否合理（固定/指数退避/抖动）、重试上限、达到上限后的最终行为。
- J6 **降级与熔断** ：下游服务异常时是否降级（返回兜底而非雪崩）、连续失败是否触发熔断、熔断后恢复策略。
- J7 **数据异常容错** ：空响应（返回空数据）、部分数据（字段缺失）、数据损坏（格式错误）时的处理，不应崩溃或返回 500。
- J8 **吞吐与资源消耗** ：TPS/QPS 吞吐、稳定性（长时间运行）、资源消耗（CPU/内存/连接数/句柄泄漏）。
- J9 **UI 感知性能阈值** ：接口性能与页面体验的桥接——页面关键接口的耗时按"用户在页面上等多久算慢"定级，而非只看接口自身 P99。约定：页面主路径接口 P95 < 2s；超阈值记「体验风险」（非硬缺陷，附 P95 数据与页面现象——loading/骨架屏/白屏表现），阈值以产品/前端约定为准，未约定时默认 2s。实测超阈值时须先排除限流与网络噪声（见 J3、关键陷阱 6/8）再下结论。

### K. 契约测试 

> 契约是"接口的合同"：字段增删、类型变更、必填性变化都会静默破坏下游，单靠功能用例发现不了。

- K1 **消费者契约**：请求-响应结构是否满足消费者的调用期望（字段是否齐全、类型是否匹配、空值语义是否一致）。
- K2 **生产者验证**：接口实际实现是否符合契约约定（OpenAPI/Protobuf 定义 vs 真实响应比对）。
- K3 **契约回归检查**：接口变更是否破坏已有契约——重点查**新增必填字段**（旧客户端未传即失败）、**字段删除/改名**、**类型收窄**（如 int → string）。
- K4 **契约版本管理**：契约文件（OpenAPI/Protobuf/Pact）是否统一管理、是否有版本策略与变更通知机制；变更类型建议明确分为 breaking / non-breaking，便于评估影响面。
- K5 **CI 自动化集成**：契约测试是否纳入流水线、契约变更时是否阻断合并并通知相关方。
- K6 **空值与默认值契约** ：字段为 null / 缺失 / 空串时，契约声明的行为与实际是否一致（高频不一致点）。四态矩阵见 B9。
- K7 **命名风格一致性** ：同一 API 内字段命名风格统一（snake_case / camelCase 二选一，不混用）；响应字段名与**接口文档**、与**前端字段**一致；URL 路径分隔符风格统一。
  > 典型缺陷：全局下划线风格中 `additionalProperty` 仍是驼峰；`eventType` 与同 API 其他接口的 `event_type` 不一致。
  > 断言 helper：`check_field_naming()`。
- K8 **文档可用性与安全** ：文档地址可访问（含相对路径拼接待验证）；在线调试可用（不 `Fail to fetch`）；**文档是否应鉴权**——全量 API 清单匿名暴露属信息泄露；CORS 是否任意 Origin 反射（可被跨域滥用）。
  > 典型缺陷：Swagger 全量 API（1009 paths）匿名可访问，且 `Access-Control-Allow-Origin` 原样反射任意 Origin。
- K9 **文档-实现一致性** ：文档声明的接口是否齐全（无遗漏）；枚举释义是否与实现一致；示例参数是否可直接跑通；必填性标注是否与实现一致。
  > 典型缺陷：枚举值 1001~1005 实为"每周限制"，文档文案写成"每年"；文档中缺失已上线的 `/v1/surveys/excel-import`。
- K10 **契约差异追踪**：对请求/响应结构做 diff 快照，记录新增、删除、改名、类型变化、默认值变化及其影响等级，便于复测和下游通知。

### L. 兼容性测试 
- L1 **向后兼容**：新版本是否支持旧版本客户端（**新增字段不影响旧解析**、旧字段废弃须有过渡期）。
- L2 **向前兼容**：旧版本客户端是否能处理新版本响应（遇到未知字段是否忽略而非报错）。
- L3 **版本迁移平滑性**：接口 URL/路径变更、版本迁移方案是否有兼容期与重定向。
- L4 **协议与序列化兼容**：REST/GraphQL/gRPC 行为是否一致；JSON/XML/Protobuf 序列化格式兼容。
- L5 **上游依赖适配**：依赖服务（第三方/内部）变更后的适配能力，是否因上游改动而静默失败。
- L6 **中间件兼容**：网关/代理/负载均衡对请求的影响（Header 改写、超时截断、Body 大小限制、连接复用）。
- L7 **客户端 SDK 兼容**：不同 SDK 版本/语言客户端的兼容性（尤其是枚举新增、字段类型变化）。

### M. 资源导出/下载 
> **适用接口**：仅导出/下载接口。创建/查询/修改等接口不适用（N/A）。
- M1 **download_url 返回**：导出接口必须返回可访问的下载链接，链接在有效期内可下载。
- M2 **导出选项生效**：导出格式选项（文本/分数/序号等）逐项验证生效，不能全部按默认格式导出。
- M3 **数据口径正确**：导出数据的总分/得分/统计值与页面一致（历史缺陷：360 问卷总分显示 N/A）。
- M4 **范围参数校验**：序号/时间范围参数校验，不能输入负数或非法范围。
- M5 **空数据导出**：按条件查询无数据时，提示"无数据"，不返回无效下载链接。
- M6 **链接有效期**：下载链接过期后失效，需重新生成；有效期与文档一致。
- M7 **文件名/结构**：导出文件名与 sheet 命名规范，与页面一致。
- M8 **权限**：无权限账号不能导出他人资源。

### N. 层级资源管理 
> **适用接口**：通讯录/标签/部门/文件夹等层级资源接口。其他业务域不适用。
- N1 **层级上限**：新增子资源必须限制层级深度（如标签只能 2 级），与页面一致。
- N2 **父级只读**：修改操作仅允许改名称，不能修改父级/层级关系（页面限制）。
- N3 **树形返回**：列表返回结构（树形/扁平）与文档一致。
- N4 **管理员三态**：设置/取消/恢复管理员的状态机——已是管理员再设置提示"已是管理员"、取消后再设置提示"需用恢复接口"、恢复非管理员提示"不是管理员"。
- N5 **admin_role 枚举**：管理员角色传枚举外值必须拒绝，不能返回成功但页面查不到。
- N6 **自定义字段**：is_visible 显示隐藏开关生效、字段类型校验、修改仅允许改名称。
- N7 **全量/部分更新语义**：全量更新未传字段清空、部分更新不传=不修改，语义必须文档明示。

### O. 异步通知/发送 
> **适用接口**：发送/通知/提醒相关接口。其他业务域不适用。
- O1 **定时发送时区**：定时时间按用户时区转换，与页面显示一致（历史缺陷：传 UTC 时间页面显示多 8 小时）。
- O2 **发送列表字段完整**：列表返回发送内容/时间/状态等字段，不能缺失。
- O3 **重新发送枚举**：重发类型枚举值语义明确，传非法值有明确提示。
- O4 **渠道枚举释义**：limit_join_type 等枚举释义正确（历史缺陷：写"每年"实为"每周"），传入范围外数字必须有失败提示。
- O5 **提醒参数**：每日提醒时间/结束日期等参数命名规范、返回完整。
- O6 **匿名渠道状态**：匿名开启后不可关闭（状态机）。
- O7 **发送内容必填**：发送内容必填且长度限制，为空不能创建成功。

### P. 分享/链接参数 
> **适用接口**：自定义链接/分享方式/渠道相关接口。360 等不支持自定义链接的类型不适用。
- P1 **渠道状态枚举**：status 传任意值必须拒绝，应为枚举值，越界提示。
- P2 **未配置时操作**：未配置链接参数时修改渠道状态，返回具体失败原因（如"还未设置自定义链接参数"），不能只报 update_failed。
- P3 **状态联动**：资源暂停/删除时，新增分享方式必须限制（与页面一致）；已删除资源新增分享提示"不存在"。
- P4 **分享方式枚举**：包含全部支持的分享方式（历史缺陷：缺内部消息枚举）。
- P5 **参数去重**：param_items 传相同 key 必须校验重复，不能落库重复参数。
- P6 **参数值长度**：参数值长度限制与页面一致。
- P7 **业务类型限制**：不支持自定义链接的资源类型必须拒绝。

### Q. 多角色关系管理 
> **适用接口**：评价/关系/多角色关联接口。普通资源接口不适用。
- Q1 **自评一致性**：设置"自评"层级时，评价人必须是被评人本人，非本人应拒绝。
- Q2 **级别数量**：支持的级别数与页面/文档一致（历史缺陷：页面可到 11 级，文档只写 5 级）。
- Q3 **覆盖语义**：is_delete_for_prev=true 时清空已有关系再新增的行为必须文档明示；=false 时重复请求应幂等。
- Q4 **已有数据限制**：已有答卷/数据时，不允许重新导入/覆盖关系（与页面一致）。
- Q5 **非目标类型拒绝**：非评价类型资源调用关系接口必须拒绝。
- Q6 **详情参数生效**：被评者详细介绍等参数必须生效。
- Q7 **级别名称**：级别名称长度限制、不允许重复。

### R. 报告/结果分享 
> **适用接口**：报告分享/结果分享接口。其他业务域不适用。
- R1 **报告类型枚举**：各报告类型枚举完整。
- R2 **分享条件**：报告分享条件（密码/有效期/权限）校验正确。
- R3 **分享方式互斥**：不同分享方式的互斥规则与页面一致。
- R4 **密码方式**：密码设置与校验正确。

### S. 容器/分类管理 
> **适用接口**：文件夹/分类/分组接口。其他业务域不适用。
- S1 **归属校验**：user_id 传空/不存在/子账号 ID 时，返回对应账号的容器，不能都返回主账号的；不存在的 user_id 必须报错。
- S2 **query_all 语义**：查询子账号容器时 query_all 参数语义必须文档说明。
- S3 **共享权限**：共享容器中的资源，接口操作权限与页面一致（历史缺陷：接口提示"不属于当前用户"但页面可操作）。
- S4 **层级口径**：容器层级起始值（从 0 还是 1）文档与实现一致。

### T. 账号/身份信息 
> **适用接口**：用户/账号/子账号信息接口。其他业务域不适用。
- T1 **字段完整**：返回 nick_name/email_verified/last_login/user_type/公司名称等字段，不能缺失。
- T2 **状态同步**：主账号状态变更（如付费）后，子账号 user_type 必须同步更新。
- T3 **命名规范**：字段命名与行业惯例/文档一致（如 date_created、email_verified 与 email 放一起）。
- T4 **描述准确**：user_name 等字段描述准确（如"用户昵称，未填写时为用户邮箱"）。
- T5 **子账号信息**：同时返回主/子账号时，子账号字段必须返回。
- T6 **账号状态**：删除/可恢复/彻底删除状态的账号，接口行为与页面一致。

### U. 批量数据导入 
> **适用接口**：导入类接口。查询/创建/导出接口不适用。
- U1 **数据合法性分级**：不存在/非数字/非选项等非法数据的落库与展示语义明确，需与产品行为对齐（历史缺陷：非选项答案显示为最后一个选项且详情为空）。
- U2 **部分成功**：导入部分成功时，成功项生效、失败项返回明细（行号/字段/原因）。
- U3 **错误定位**：excel/文件导入报错需给出明确错误定位（行号/字段）。
- U4 **重复导入**：重复导入的幂等性。
- U5 **导入数量边界**：批量导入大数量的边界与性能。

### V. 请求标识与追踪 
> **适用接口**：所有接口（请求头层）。仅在接口文档要求 X-Request-Id 时测试。
- V1 **全局唯一性**：X-Request-Id 需保持单用户全局唯一，重复使用的处理需明确（幂等/请求追踪）。
- V2 **与签名关系**：X-Request-Id 是否需与加密/签名时一致，需文档明确。
- V3 **格式校验**：X-Request-Id 格式（如 UUID）校验。
- V4 **缺失处理**：不传 X-Request-Id 时接口行为（自动生成/拒绝）需文档明确。
- V5 **链路可观测性**：请求 ID / trace ID / correlation ID 能否贯穿接口响应、日志与下游调用，便于最小复现与排障。
- V6 **幂等键**：若接口支持 idempotency-key / request nonce，重复提交、超时重试、跨实例重放时语义须明确。

### W. 文件/附件管理 
> **适用接口**：含附件/上传题/签名题的详情接口。无附件题型的接口不适用。
- W1 **附件字段完整**：file_views/file_downloads 等附件查看/下载次数字段返回正确。
- W2 **签名题**：签名题返回结构与图片可访问。
- W3 **附件链接有效期**：附件链接过期后失效，需重新生成。
- W4 **附件类型限制**：支持的附件类型与页面一致。
- W5 **文件类型与 MIME**：下载文件的 Content-Type / 文件扩展名 / 实际内容一致，不可只靠链接可访问。
- W6 **内容完整性**：大文件、压缩包、分片上传/断点续传场景下，文件内容、顺序与校验值不丢失。
- W7 **导入导出回显**：导入/导出后的文件名、编码、sheet 名称与页面/文档说明一致。

### X. 批量操作 
> **适用接口**：批量操作接口（批量修改/批量删除/批量导入）。单条操作接口不适用。
- X1 **部分成功语义**：批量操作中部分项失败时，成功项应保存成功、失败项返回失败明细（历史缺陷：一个有问题整体报错，其他都改不了）。
- X2 **删除数量返回**：批量删除必须返回删除数量。
- X3 **与事件联动**：批量删除必须触发 webhook/事件并记录数量。
- X4 **批量幂等**：重复批量操作的幂等性。

### Y. 复杂结构返回 
> **适用接口**：返回复杂嵌套结构的详情/查询接口。列表/简单接口不适用。
- Y1 **子类型结构完整**：各子类型返回结构完整，不能缺字段。
- Y2 **选项属性**："按标签显示""选项填空默认提示"等设置参数必须返回（历史缺陷：导出 JSON 缺这些参数导致重建不对）。
- Y3 **嵌套正确**：矩阵/表格/多级下拉等嵌套结构正确。
- Y4 **类型与结构对应**：返回的 type 字段与实际结构匹配。

### Z. 国际化/多语言 
> **适用接口**：多语言相关接口。单语言接口不适用。
> **默认不适用**：国内版测试中本节一律标 **N/A**。完整场景（Z1–Z8）见 §1.3 国际版扩展，仅在满足该节启用条件时加载。
- Z1–Z5、Z6–Z8 共 8 个场景的完整定义见 **§1.3**。

### AA. 分页与列表查询 
> **适用接口**：所有列表 / 分页查询接口。单条详情接口不适用（N/A）。
- AA1 **页码边界**：`page_index` = 0 / 负数 / 超大值 / 非数字 → 行为须定义（拒绝或返回空），**不能 500、不能静默返回首页数据**。
- AA2 **每页条数边界**：`page_size` = 0 / 负数 / 超大值（如 100000）→ 须有上限保护。
- AA3 **总数一致性**：`total` 与实际返回条数、翻页累计条数一致；末页不重复不遗漏。
- AA4 **末页行为**：超范围页码返回空数组还是报错，须文档化且稳定。
- AA5 **排序**：排序字段合法/非法、升/降序、**排序稳定性**（同值多次请求顺序一致）。
- AA6 **筛选**：单条件 / 多条件组合；**筛选条件无效时应返回空，严禁静默返回全量**（典型缺陷：state 参数筛选不出来，返回的是全部数据）。
- AA7 **筛选字段命名**：与文档及其他接口一致（`state` vs `status` 类问题属缺陷）。
- AA8 **空结果**：无数据时返回空数组 + `total=0`，不报错、不返回 `null`。
- AA9 **字段冗余**：列表级常量字段应上提至响应顶层，不逐条重复（如"是否匿名"在每条记录都返回属冗余）。
- AA10 **游标 / Token 翻页**：`cursor` / `pageToken` / `nextToken` / `offset` 翻页要验证连续性、不可重复/漏数据、token 失效或篡改时行为明确；排序条件变化时 token 不得静默复用。
> 断言 helper：`check_pagination()`。

### AB. 前端-接口口径一致性 
> **适用接口**：所有有对应页面的接口。纯内部服务接口不适用（N/A）。
> **为什么单列**：这是**纯接口视角 100% 测不出来**的一类缺陷——接口自身跑得通，但与前端口径不一致，用户实际用起来就是坏的。历史缺陷中占比约 8.4%，为第二高发模式。
> **观测方法**：把**页面基线**（页面操作结果 / 页面显示值）作为预期值写入用例，而非只看接口返回。
- AB1 **权限口径**：同一资源同一操作，**页面可操作 ⟺ 接口可操作**。共享 / 协作 / 子账号 / 资源管理员等场景必测。
  > 典型缺陷：共享文件夹中的问卷，问卷管理员在页面可修改，接口却报"The survey does not belong to the current user"；分配给问卷管理员的问卷，接口允许删除而页面不允许。
- AB2 **校验口径**：页面允许为空 / 允许某取值 ⟺ 接口同样允许（联动 B8 过度校验）。
- AB3 **展示口径**：时间（时区 / 格式）、状态文案、枚举释义，接口返回值与页面显示一致。
  - **错误提示透传**（H9/陷阱16 的前端延伸）：接口错误码 ↔ 页面提示文案映射一致；前端不得用通用兜底文案（如"操作失败，请重试"）**掩盖根因**，也不得展示未渲染的模板占位（`{0}`、`Email[]`）。实测方法：构造两类不同成因的错误请求，观察页面提示是否可区分（`check_error_root_cause()` 验接口层 + `check_ui_parity(aspect="错误提示")` 验页面层）。
- AB4 **枚举口径**：接口枚举取值集合与页面下拉选项集合一致（不多不少）。
- AB5 **默认值口径**：未传字段的默认值，与页面新建时的默认值一致。
- AB6 **边界口径**：长度 / 数量 / 层级上限，与页面限制一致。
> 断言 helper：`check_ui_parity()`。

### AC. 幂等与业务唯一性 
> **适用接口**：所有写接口（创建 / 修改 / 删除）。纯查询接口不适用（N/A）。
- AC1 **重复请求幂等**：相同参数的写请求连续提交 N 次 → 只产生 1 份数据，或明确返回"已存在"。
- AC2 **业务唯一性校验**：邮箱 / 手机号 / 名称 / ID 等应唯一的字段，重复时必须拒绝。
- AC3 **列表型参数去重**：ID 列表 / key 列表传重复值 → 去重或报错，不静默产生重复数据。
  > 典型缺陷：重复的 IP 段无限制、标签 Id 列表未去重、已是非管理员的联系人重复设置成功。
- AC4 **错误信息归属**：唯一性冲突的提示语必须指向**正确的对象名**，并在错误信息中**回显冲突值**。
  > 典型缺陷：自定义字段名重复，提示语却写"标签名不能重复"；邮箱重复时提示 `Email[]` 未回显实际邮箱。
- AC5 **并发幂等**：并发提交同一请求 → 不产生重复数据（与 J2 并发正确性联动）。
- AC6 **无唯一键时的幂等观察** ：契约未声明业务唯一键时，重复提交是否被去重属业务未知量——
  创建出多个不同对象只记**观察**（`check=idempotent`），只有"结果漂移"（两次响应既不一致也不是新建对象）才判缺陷。
> 断言 helper：`check_uniqueness()` · `check_idempotent()` · `check_concurrency()`。

### AD. 事件与回调 
> **适用接口**：所有会触发事件 / 回调的接口，以及 Webhook 管理接口本身。无事件机制的接口不适用（N/A）。
- AD1 **事件完备性**：文档声明的每个事件类型都能被真实触发并推送（**枚举遍历**，不能只测一个）。
- AD2 **不丢失**：触发 N 次 → 收到 N 条；批量操作须明确推送 N 条还是 1 条（含数量字段）。
- AD3 **不重复**：一次触发只推一条；不因"全局订阅 + 按用户订阅"叠加而重复推送。
  > 典型缺陷：创建问卷后同时产生 1 条"创建" + 1 条"更新"记录。
- AD4 **载荷准确**：载荷字段值与实际一致（如"无效原因"枚举值、"删除数量"）。
- AD5 **订阅范围矩阵**：全局 / 按用户 / 按资源 × 主账号 / 子账号 的推送归属须定义清晰且稳定。
  > 典型缺陷：创建了 8 个 Webhook 只推了 1 个；按子账号订阅的事件触发了却无推送记录。
- AD6 **前置状态约束**：订阅对象处于非常规状态（审核中 / 已删除）时的行为须定义。
- AD7 **失败重试与补推**：接收端返回 5xx 时是否重试、重试次数与退避、是否可手动补推。
- AD8 **顺序性**：同一资源连续事件是否按发生顺序送达。
- AD9 **并发一致性**：并发触发时推送条数与实际一致（实测曾出现实际 50 条、日志仅 31 条）。
> 断言 helper：`check_event_delivery()`；Webhook 基础验证用 `webhook_verify()`。

## 3. 场景设计三要素模板

每个场景按以下结构描述（先设计、后实现脚本）：

```
【场景编号】维度-序号  （如 C1、G2、K3）
【场景名称】一句话描述
【输入要点】对哪些参数做了什么变异（值、类型、组合）
【观测点】  断言什么（响应码/result/错误语义/回读数据/渲染结果/DB落库）
【预期行为】通过判定（含"符合预期的安全拦截"等非缺陷结论）
【优先级】  P0/P1/P2
【依赖环境】低依赖(测试环境可直接复现) / 特定账户(需特定配置) / 深化(可选)
【可自动化】是/否/部分
```

> 示例（脱敏、不绑业务）：
> ```
> 【C1】更新后数据真值回读
> 【输入要点】创建对象 obj；调用更新改 title=T2、content=C2
> 【观测点】更新返回成功后，通过查询/公开页读回 obj 的 title 与 content
> 【预期行为】读回值 == T2/C2（证明确实生效）；若读回仍为旧值→缺陷
> 【优先级】P1  【依赖环境】低依赖  【可自动化】是
> ```

### 3.1 观测点写法：断言三层次 

「观测点」不要只写"返回成功"，必须落到下面三层，写操作用例**必须含 DB 层**：
| 层次 | 断言内容 | 写法示例 |
|---|---|---|
| **1. 状态断言** | HTTP 状态码 / 响应码 | `HTTP 200` / `$.code == 0` / `HTTP 400` / `401` / `403` / `409` |
| **2. JSONPath 断言** | 响应体关键字段 | `$.data.fieldName == expectedValue` |
| **3. DB 断言**（写操作必须） | 数据库记录变更 | `DB: table.field = expectedValue WHERE condition` |
> 规则：**只有状态断言的用例 = 假通过高风险**。凡是创建/更新/删除类场景，必须补 DB 断言或等价回读断言（对应 C6）。

### 3.2 前置条件三要素 

每条接口用例的前置条件必须写全三项，缺一项就容易出现"用例不可复现 / 判定失真"：

1. **认证信息**：有效凭证的获取方式（如「通过 `/api/auth/login` 获取有效 JWT Token，账号 X、角色 Y」）。
2. **测试数据构造**：接口依赖的数据状态（对象已存在？处于哪个状态？关联数据是否就绪？）。
3. **环境要求**：接口服务状态、依赖服务（第三方/下游）是否就绪、是否需 Mock（见 §9.5）。

## 5. 分层与优先级策略

按**依赖风险**与**实现成本**分层，建议执行顺序：

- **L0 冒烟**：主链路成功路径（D1）+ 必填项齐全 → 先证明"接口能用"。
- **L0.5 业务场景（AF，可选）**：AF1 主业务流 / AF2 业务规则 / AF3 业务组合 → 补"用户实际怎么用"。
  默认关闭，需显式启用；启用后与 D 并列执行，成本略高但能命中纯技术视角测不出的问题。
- **L1 参数校验**：B1–B9（含 B8 过度校验、B9 空值四态）→ 成本低、易发现基础缺陷。
- **L2 字段真值 + 状态机**：C 系列（回读/DB 断言）+ E 系列（生命周期，含 E6 重复操作提示、E7 非法前置态）→ 补"假通过"盲区，**性价比最高**。
- **L3 安全 + 权限 + 组合**：A、G、F → 需特定账户/配置准备（在指定环境内即可，不要求多环境）。
- **L4 契约 + 口径 + 分页**：K 系列（含 K7 命名风格、K8 文档安全、K9 文档一致性）+ AA 分页 + AB 前端一致性 → 需页面基线与契约文件；**AB 是纯接口视角的盲区，优先级等同于 L2**。
- **L5 幂等 + 事件**：AC 幂等唯一性 + AD 事件回调 → 需构造重复数据与事件接收端。
- **L6 兼容**：L 系列 → 需多版本客户端。
- **L7 性能 + 深化**：J 系列（含超时/重试/降级/熔断、J3 限流配额口径）→ 通常单独立项。
> 国际版维度（§1.3）仅在启用时插入 L2 之后执行，国内版跳过。

**环境依赖分层**（避免卡在不可复现项）：
1. 低依赖环境（通用测试账号即可复现）先行；
2. 特定账户/配置（需 <跨企业appid> 类专属账号、后台开关）靠后，标注"需专项/指定环境"；
3. （仅当做了多环境对比时）多环境行为不一致统一归入 **ENV 台账**，不擅自判缺陷；默认单环境测试可跳过此条。

## 6. 常见"假通过"盲区检查清单

执行前逐条自查，避免"用例全绿但没测出问题"：

> **运行期已内置门禁（v3.17，详见 SKILL.md「防呆门禁」章）**：① `config_consistency_check()` 启动阶段拦截 region / 跨环境 / 域名矛盾；② `coverage_gate()` 收尾时比对 `COVERAGE_PLAN` 声明维度与实际执行维度，缺口即记【缺陷(覆盖率缺口)】（`WJX_STRICT_COVERAGE=1` 时 exit(2)）；③ 仅断言 `result=true` 的浅用例记低危观察并汇总告警，`assert_non_empty()` / `check_enum_exhaustive()` 防"空转假通过"。建议在 `main()` 声明 `COVERAGE_PLAN` 以启用反漏测。

- [ ] 是否只验 `result=true` / HTTP 200，**从不回读验证数据真落库**？（C 系列）
- [ ] *(针对 B 参数校验，最隐蔽盲区)* 参数校验用例是否把"非法/缺失/类型错/枚举越界输入**应被拒绝**"误断言成"**应当成功**"？（宽松接口接受非法值 → 用例判 PASS → 缺陷被完全掩盖；对应 1006001 漏报 5 条缺陷）
- [ ] 因子矩阵是否只"记录"结果、或只对"本应成功却失败"记问题单，**没对"本应被拒绝却接受"记问题单**？（F 系列）
- [ ] 是否只验响应字段**非空**，不验其**语义有效性**？（如返回的 URL 能否真渲染）
- [ ] 异常用例是否只验"失败"，**不验错误语义是否具体**？（H 系列）
- [ ] 边界是否**只在单字段**测，没做组合？（F 系列）
- [ ] 并发用例是否只验"请求被接受"，**不验最终一致性/脏写**？（J2，需读回手段）
- [ ] 安全用例是否把"被正确拦截"误记成**缺陷**？（G1 类属预期行为）
- [ ] （仅当做了多环境对比时）多环境差异是否当成缺陷或当成正常而**未记录**？（ENV）
- [ ] 更新接口是否验证了"未传字段保留原值"？（C2）
- [ ]  写操作用例是否**只有状态断言**，缺 JSONPath / DB 断言？（§3.1）
- [ ]  契约用例是否只测"接口能通"，**没测字段结构是否悄悄漂移**？（K3）
- [ ]  兼容性是否只测新版本，**没测旧客户端能否解析新增字段**？（L1/L2）
- [ ]  超时/重试用例是否只验"最终成功"，**没验重试次数与退避策略**？（J4/J5）
- [ ]  是否依赖真实第三方导致用例不稳定，**未用 Mock 隔离异常场景**？（§9.5）
- [ ]  前置条件是否缺"认证/数据/环境"任一项，导致用例不可复现？（§3.2）
- [ ]  **是否只测了"欠校验"，没测"过度校验"**——可选/可空字段传 null/空串/不传 应成功却被拒，被人工归因为"需求就这样"而漏报？（B8/B9，"假失败"盲区）
- [ ]  **是否做过"读接口返回值直接回写给写接口"的往返验证**？（B8 高发触发点）
- [ ]  **列表接口是否只验"能返回数据"，没验筛选是否真生效**？（AA6，筛选无效时静默返回全量属缺陷）
- [ ]  **分页是否只测了第 1 页**，没测页码/条数边界与 total 一致性？（AA1–AA3）
- [ ]  **是否与页面基线比对过**（权限/校验/展示/枚举口径）？纯接口视角测不出前后端不一致（AB 系列）
- [ ]  写接口是否测过**重复提交**与**业务唯一性冲突**？（AC1/AC2）
- [ ]  会触发事件的接口是否验过**事件真的推送了**，而不只是"Webhook 创建成功"？（AD1/AD2）
- [ ]  错误信息是否验过**根因没被掩盖**——凭证错误与参数缺失的报错是否相同？（H6）
- [ ]  错误信息中是否残留**未渲染的模板占位**（`{0}` / `%s` / `Email[]`）？（H7）
- [ ]  终态对象**重复同一操作**是否静默返回 true 而无提示？（E6）
- [ ]  是否断言了 **HTTP 状态码语义**（400/401/403/404/409/429），而非只看业务 result？（P2-3，见 §9.7）
- [ ]  响应字段**命名风格**是否与同 API 其他接口、与文档、与前端一致？（K7）
- [ ]  **回归复测时，套件期望是否已随接口修复同步更新**？修复后旧期望会把已修好的缺陷再次误报成 FAIL（过期期望陷阱）
- [ ]  **检查逻辑是否引用了已改名的响应字段**？接口改字段名后取不到值，校验循环空转恒 PASS（空转假通过）
- [ ]  **套件里的 finding 是否硬编码无条件记录**？检查 PASS 也会把旧缺陷文案写进台账，复测结论被污染
- [ ]  **复测后台账是否回写了最新结论**（状态+证据），并与基线对照区分"已修复/仍存在/新发生"？

## 8. 问题记录规范格式（通用）

每条问题统一字段，便于结构化追踪与复盘：

```
编号 | 类型 | 严重程度 | 状态 | 问题描述(现象化) | 请求参数(Body) | 预期结果 | 实际结果
```

- **类型**：缺陷 / 待确认 / 环境风险(ENV) / 已确认非问题 / 符合预期(安全拦截)
- **严重程度**：高 / 中 / 低 / 信息
- **状态**：待修复 / 符合预期 / 待确认 / 已确认非问题
- **问题描述**：用**现象**口吻，避免纯技术术语（例："在内容里写入网页脚本也能保存，需确认别人打开时脚本会不会真的被执行"）。
- **请求参数**：保留完整请求 Body，便于复现。

> 导出 CSV 时用 `UTF-8 with BOM`（`utf-8-sig`）逗号分隔，字段含逗号/引号/换行时用双引号包裹，避免 Excel/WPS 打开异常。

```

```

### 9.4 接口串联与辅助验证 

#### 9.4.1 串联模板（基础）
```
步骤N：调用 A 接口，保存返回的 $.data.orderId
步骤N+1：使用步骤N返回的 $.data.orderId 作为本步骤入参
前置条件：说明依赖接口的调用顺序（A → B → C）
失败处理：链路上游失败时，是否跳过下游 / 是否回滚（对应 D6）
```

#### 9.4.2 辅助验证接口矩阵（核心）
> **原则**：测试主接口时，不只看主接口的响应，应调用其他独立接口做交叉验证。辅助接口与主接口越独立，验证可信度越高。
> **优先级**：独立详情查询 > 列表查询 > 统计/计数 > 下载链接可访问 > Webhook 日志 > DB 直查。
| 主接口操作 | 推荐辅助接口 | 验证点 | 断言示例 |
|-----------|------------|--------|---------|
| **创建** | 详情查询接口 | 新资源存在、字段与请求一致 | `query(vid).title == 请求的 title` |
| **创建** | 列表查询接口 | 新资源出现在列表中、排序位置正确 | `list() 包含 vid，且在第一页` |
| **创建** | 统计/计数接口 | 总数 +1 | `count() == 原 count + 1` |
| **修改** | 详情查询接口 | 修改字段生效、未传字段保留原值 | `query(vid).title == 新值; query(vid).desc == 原值` |
| **修改** | 列表查询接口 | 列表中显示已更新 | `list() 中 vid 的 title 为新值` |
| **删除** | 详情查询接口 | 资源不存在或标记已删除 | `query(vid) 返回不存在 / status=已删除` |
| **删除** | 列表查询接口 | 资源从列表消失 | `list() 不包含 vid` |
| **删除** | 统计/计数接口 | 总数 -1 | `count() == 原 count - 1` |
| **状态变更**（发布/暂停/恢复） | 详情查询接口 | 状态字段正确 | `query(vid).status == 预期状态` |
| **状态变更** | 公开访问接口 | 状态生效（如发布后可公开访问） | `公开页 HTTP 200 / 暂停后 403` |
| **导出** | 下载链接 | 链接可访问、文件内容正确 | `HEAD(download_url) == 200; 文件行数 == 预期` |
| **导入** | 详情/列表查询接口 | 导入数据落库、数量正确 | `list() 新增 N 条; 字段与导入文件一致` |
| **批量操作** | 列表/详情查询接口 | 成功项生效、失败项不变 | `成功项状态已改; 失败项状态不变` |
| **权限变更** | 子账号调用接口 | 权限生效/失效 | `子账号 query(vid) 从 403 变 200 或反之` |
| **Webhook 配置** | Webhook 日志接口 | 事件触发并推送 | `webhook_logs 含 event_type，payload 正确` |
| **配置变更**（限流/IP） | 实际调用接口 | 配置生效 | `超限后被限流; 白名单 IP 可访问` |
#### 9.4.3 辅助验证三层次断言
对辅助接口的返回做三层断言，逐层加深：
1. **存在性**：资源是否存在/消失（最浅，如 `query(vid)` 不报错）
2. **字段一致性**：关键字段与主接口请求/预期一致（如 `title == 新值`）
3. **副作用完整性**：关联数据/统计/级联是否正确（如 `count +1`、子资源同步变更）

> 只做第 1 层 = 弱验证（可能"假通过"）；至少做到第 2 层，关键场景做到第 3 层。

#### 9.4.4 辅助验证失败的归因
辅助接口返回异常时，**不要直接判主接口缺陷**，先归因：
| 现象 | 可能原因 | 处理 |
|------|---------|------|
| 辅助接口超时/5xx | 辅助接口本身故障或环境问题 | 重试；仍失败记 ENV，不判主接口缺陷 |
| 辅助接口返回数据延迟 | 主从同步/最终一致性 | 等待后重试（建议 1-3s，最多 3 次）；仍不一致再判缺陷 |
| 辅助接口权限不足 | 测试账号无权限 | 换有权限账号，不判缺陷 |
| 辅助接口字段与主接口不同步 | 真实数据不一致缺陷 | 记缺陷，附两个接口的完整请求/响应 |
| 辅助接口不存在 | 系统无此查询能力 | 降级到 DB 断言或标注"无法辅助验证" |
#### 9.4.5 辅助接口选择原则
- **优先用读接口**（查询/列表/统计）做验证，避免用写接口验证写接口（互相污染）。
- **辅助接口应与主接口独立**：如测创建接口，用详情查询接口回读，而不是再调创建接口。
- **辅助接口本身应已通过冒烟测试**：否则验证结果不可信。
- **记录辅助接口调用**：在测试报告中注明"本用例通过 XX 接口辅助验证"，便于复现。

### 9.5 Mock 策略 

需要 Mock 的场景（否则用例不稳定或无法构造）：
- **第三方服务**：支付、短信、地图、身份认证等外部依赖
- **不稳定服务**：外部依赖偶发超时/故障
- **开发中服务**：接口尚未就绪，需先用 Mock 联调
- **特殊场景构造**：异常、超时、限流、数据损坏等难以在真实服务触发的场景（对应 J4–J7）
- **测试数据**：特定数据构造成本高

常用 Mock 工具：
| 工具 | 适用 |
|---|---|
| WireMock | Java 生态，功能全面 |
| MockServer | 轻量级，易于使用 |
| Postman Mock | 在线 Mock 服务 |
| MSW | 前端 Mock，请求拦截 |
| 自建 Mock（Python/Node 脚本） | 灵活定制异常与延时 |
> 注意：Mock 用例须标注"依赖 Mock"，避免与真实链路用例混淆；契约测试（K）不宜对被测方做 Mock，否则测不到真实契约。

### 9.7 HTTP 状态码语义映射表

> 只判断"是否 5xx"远远不够。业务错误码与 HTTP 状态码的映射必须一致，否则网关、SDK、重试逻辑会全部误判。

| 业务语义 | 期望 HTTP 状态码 | 常见误用 |
|---|---|---|
| 参数缺失 / 格式错误 / 枚举越界 | **400** | 返回 200 + 业务失败码（伪成功） |
| 未提供凭证 / 凭证失效 / 签名错误 | **401** | 与 403 混用 |
| 已认证但无权限（越权操作） | **403** | 与 401 混用、或返回 200 |
| 资源不存在 | **404** | 资源实际存在却返回 404（路由/权限问题） |
| HTTP 方法不允许 | **405** | 返回 400 |
| 冲突（唯一性冲突 / 状态冲突） | **409** | 返回 400 或静默成功 |
| 限流 | **429** | 返回 200 + 业务码，客户端无法识别需退避 |
| 服务端异常 | **5xx** | 一律记缺陷（即使业务"正常"） |

**测试要点**
1. **401 与 403 必须区分**：无凭证应 401，越权应 403。二者混用即为缺陷——客户端无法判断该重新登录还是申请授权。
2. **伪成功检测**：业务失败但 HTTP 200 时，先确认是否为文档化约定（单 POST JSON 网关常见）；**未约定则记问题**。
3. **状态码与业务码双断言**：同一响应必须同时校验 HTTP 状态码与业务错误码，任一不符即记缺陷。
4. **限流必须可识别**：限流响应须带约定状态码与恢复时间提示，否则客户端无法退避，会持续打爆服务。
> 断言 helper：`check_http_semantics()`。

## 10. 使用示例（脱敏示意，不绑定具体业务）

> 假设要测"资源创建 / 资源更新"两个动作：
> 1. 套用 §1.1 识别协议（假设为类 RPC 的单 POST 网关动作，按 RESTful 对待，但注意无状态语义弱化）。
> 2. 套用 §2：先确认 A（签名）、B（必填/枚举）、C（更新后回读）、E（创建→发布→暂停→更新→删除）四大类，再按 §1.2 校验用例数达中等接口配额（×10）。

## 11. 测试数据管理规范

> 测试数据污染是"用例不稳定 + 结论被误判"的头号来源。本节规范数据的**构造、隔离、清理**三个环节。

### 11.1 命名规范
- 所有测试资源统一前缀：`TEST_AUTO_<用例号>_<随机串>`（如 `TEST_AUTO_B8_7f3a`）。
- **禁止裸名**（如"测试问卷1"），否则无法区分历史数据与本轮数据。
- 随机串用于绕过防重提交与限流（见关键陷阱 6）。

### 11.2 数据工厂
- 前置数据（依赖的问卷 / 联系人 / 分组等）用**工厂函数**构造（如 `make_survey()` / `make_contact()`），禁止每个用例内手写一堆参数。
- 工厂函数负责：默认值填充、随机串拼接、创建后返回资源 ID。
- 好处：契约字段变更时只改工厂，不必改所有用例。

### 11.3 用例级清理
- 每个用例在 `try/finally` 中调用 `teardown()`，**即使断言失败也执行清理**。
- **崩溃安全**：创建资源后立即用 `register_cleanup()` 登记到清理清单（立即落盘）——用例中途异常、进程被杀后，仍可用 `--cleanup-only` 补删（见 11.4）。
- 清理失败不判用例失败，但须记录到"环境残留清单"。

### 11.4 孤儿数据兜底
- 用例中途异常、进程被杀、网络中断都会留下孤儿数据。
- 整轮结束后**按前缀扫描残留资源并清理**；运行器提供 `--cleanup-only` 模式单独执行清理（读取 `cleanup_manifest.jsonl` 清理清单，成功条目自动移除、失败条目保留待重试）。
- 建议每轮测试开始时先跑一次清理，避免上一轮残留干扰。

### 11.5 并发数据隔离
- 并发用例中**每个线程必须使用各自独立构造的资源**，禁止多线程共享同一资源 ID（否则互相污染，产生"数据串了"的假缺陷）。
- 资源构造成本高时，用工厂函数批量预建后按索引分配。

### 11.6 不可删资源的处理
- 部分资源无法删除（如已发布且已收集数据的对象、配额受限资源）。
- 处理策略：标记后**复用**（不重复创建），或明确记入"环境残留清单"并说明原因。
- 复用时须注意状态污染——复用前重置为已知初始状态。

### 11.7 依赖声明
- 用例三要素模板的**前置条件**必须声明依赖数据与构造方式（见 §3.2）。
- 未声明依赖的用例换环境必然跑不通，且他人无法复现。

### 11.8 为 UI 测试供数（接口测试对 UI 的输出价值）
- **UI 自动化用例的前置数据应通过本 skill 的接口工厂构造**，而不是在 UI 里一步步点出来——接口造数快（毫秒级）、稳定（不受页面改动影响）、可批量。
- 交付物是一份**可消费的数据清单**：账号 + 资源 ID + 状态（如 `TEST_AUTO_UI_*` 前缀的问卷 vid 列表及其状态），UI 用例按清单直接进入目标状态（已发布/已收集/已删除等）。
- **双向衔接**：① UI 用例失败时，先跑对应接口的冒烟/单接口请求定位归属——接口正常则问题在前端，接口同样失败则为后端缺陷；② 接口新增/改名字段时，主动提醒 UI 侧核对 AB 口径（见 §AB、`ui_baseline.md`）。
- 供数资源同样遵守本节命名/清理规范；UI 跑完后可由接口侧 `--cleanup-only` 统一兜底清理。
